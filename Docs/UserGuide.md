## 1. Как устроен RCynQ

RCynQ синхронизирует рабочую копию разработчика с закрытым Git-репозиторием, к которому нет прямого доступа. Узлы соединяются в цепочку по SSH, при необходимости поверх VPN-туннеля.

```
 Source ──ssh──▶ Mediator ──ssh──▶ … ──ssh──▶ Dest
 (рабочая копия)   (ретранслятор)             (закрытый репозиторий)
```

| Роль | Что делает | Чего не делает |
|------|------------|----------------|
| **Source** | Хранит рабочую копию. Отправляет изменения на Dest и принимает их оттуда. Получает ветки Git только с Dest (`fetch`, fast-forward `pull`). | Никогда не делает `push`. |
| **Mediator** | Ретранслирует SSH-соединения и поднимает транспорт (Direct или AmneziaWG). | Не видит содержимого: патчей и Git у него нет. |
| **Dest** | Хранит закрытый репозиторий. Принимает и применяет патчи, отдаёт ветки через `git-upload-pack`, отправляет изменения обратно на Source. | — |

### Как ходят изменения

1. У каждого узла есть **база синхронизации** — то, что точно есть у соседа. Для Git-репозитория она строится **автоматически** из коммита, общего для обоих узлов: на Dest это `HEAD`, на Source — коммит Dest, на котором стоит рабочее дерево (его приносит Pull). После каждого обмена в базу попадают переданные файлы, а после нового коммита (Pull на Source, коммит на Dest) она пересобирается. Делать деревья одинаковыми и создавать что-то вручную не нужно. Только для папки **без Git** база — это ручная **базовая копия** (снимок рабочего дерева, раздел 4.6).
2. Узел собирает **патч** — текущий Git diff без того, что у соседа уже есть: список файлов, отличающихся от базы синхронизации, с хэшем SHA-256 и размером каждого, а также хэш версии, от которой отправитель считал изменение. Файлы и папки, которые описаны в `.gitignore` или в `ExcludedDirectories`, в патч не попадают (раздел 6.2а).
3. Патч подписывается ключом узла (ECDSA P-256) и отправляется **сессией** через SSH-форвард по цепочке (или на TLS-порт узла без SSH-сервера):
   1. на Dest уходит подписанный **манифест** (список файлов и хэшей), сжатый gzip. Dest проверяет общий link-токен, отправителя, подпись, срок жизни патча и повторную отправку и отвечает, каких файлов у него ещё нет;
   2. каждый недостающий файл отправляется **отдельным запросом**: Source читает его с диска и сжимает gzip на лету, Dest распаковывает и принимает, только если размер и хэш совпали с подписанным манифестом. Одновременно в памяти лежит только небольшой кусок файла, поэтому размер проекта не ограничен общим лимитом: ограничен только один файл (500 МБ). Если связь оборвалась, повторная отправка не пересылает файлы, которые Dest уже получил;
   3. когда все файлы на месте, Source просит Dest применить патч.
4. Dest применяет патч **атомарно**: либо все файлы, либо ничего. Разницу (diff) для просмотра Dest строит сам из своей базы синхронизации, по сети она не передаётся.
5. Файл применяется без вопросов, если на Dest он всё ещё такой, от какого отправитель считал изменение. Если файл на Dest изменили (в том числе закоммитили) после этого, патч получает статус **«конфликт»** и ждёт решения пользователя.

В обратную сторону, Dest → Source, всё работает так же.

### Компоненты на каждом узле

| Программа | Назначение |
|-----------|------------|
| `RCynQ.UI` | Графическое приложение (Avalonia). **Само запускает сервис узла** в выбранной роли и **останавливает его при закрытии** — вместе с туннелями и SSH-форвардами. |
| `RCynQ.Service` | Сервис узла. Держит локальный API на `127.0.0.1:<ListenPort>`, принимает патчи, поднимает транспорты. Обычно запускается приложением; на серверах без графики — отдельно (раздел 3.5). |
| `rcynq` | CLI. Работает с данными узла напрямую, запущенный сервис для большинства команд не нужен. |
| `RCynQ.Dbs.SQLite.DbMigrator` | Ручное применение миграций базы. Обычно не нужен: сервис и CLI мигрируют базу сами. |

## 2. Требования

### Все узлы

- **ОС:** Windows 10/11, Linux x64 или macOS (arm64).
- **.NET:** для self-contained сборок рантайм не нужен. Из исходников нужен .NET SDK 10.
- **SSH-клиент:** OpenSSH (`ssh`, `ssh-keygen`, `ssh-keyscan`) в `PATH` или по путям из раздела `Ssh`.
- **Свободный локальный порт** сервиса, по умолчанию `18443`. Сервис слушает только loopback, открывать порт в файрволе не нужно.

### По ролям

| Роль | Что нужно дополнительно |
|------|-------------------------|
| **Source** | `git`. Сервер `sshd` — чтобы Dest мог присылать изменения обратно. |
| **Mediator** | Сервер `sshd`, доступный соседям. Для AmneziaWG — `awg` и `awg-quick` (Linux/macOS) или `amneziawg.exe` (Windows) и права на поднятие туннеля. |
| **Dest** | `git`, `sshd`, сам репозиторий. |

## 3. Установка и запуск

### 3.1. Сборка дистрибутива

Дистрибутив собирается из исходников на любой машине с .NET SDK:

```powershell
# Windows (win-x64)
./Scripts/publish-win.ps1
```

```bash
# Linux (linux-x64)
./Scripts/publish-linux.sh
# macOS (osx-arm64)
./Scripts/publish-macos.sh
```

Другой runtime передаётся первым аргументом, например `./Scripts/publish-linux.sh linux-arm64` или `./Scripts/publish-win.ps1 -Runtime win-arm64`.

Результат появится в `artifacts/publish/<runtime>/`:

```
RCynQ.exe       запуск приложения (Windows, с иконкой RCynQ); RCynQ.sh (Linux, macOS) — работают из любого места
RCynQ.desktop   ярлык запуска (Linux) или RCynQ.command (macOS)
rcynq.portable  метка портативной установки
service/        RCynQ.Service
cli/            rcynq
ui/             RCynQ.UI
dbmigrator/     RCynQ.Dbs.SQLite.DbMigrator
```

Рядом создаётся **чистый пакет для раздачи**: `artifacts/publish/RCynQ-<runtime>.zip` (Windows) или `RCynQ-<runtime>.tar.gz` (Linux, macOS). В нём та же раскладка в папке `RCynQ/`, но без `config/`, `data/` и ярлыка с абсолютными путями — даже если вы уже запускали приложение из каталога публикации.

**`RCynQ.exe`** запускает приложение, а приложение поднимает сервис узла. В нём нет абсолютных путей, поэтому папку можно переносить целиком. Для Windows можно также собрать установщик: `./Scripts/build-installer.ps1` (см. README).

### 3.2. Размещение на узле

1. Распакуйте на узле чистый пакет `RCynQ-<runtime>.zip` / `.tar.gz`, **сохранив структуру**: приложение ищет сервис в соседнем каталоге `service/`. Не копируйте каталог, из которого приложение уже запускалось, — см. «Перенос и копирование» ниже.

   | ОС | Рекомендуемое место |
   |----|---------------------|
   | Windows | `C:\RCynQ\` — не `C:\Program Files`: программа хранит данные в своей папке, и туда нужно право записи |
   | Linux | `~/RCynQ/` |
   | macOS | `~/Applications/RCynQ/` |

   Пробелы в пути допустимы: пути к SSH-ключу и к `known_hosts` RCynQ записывает в собственный файл настроек SSH (`data/keys/ssh_config`), где они берутся в кавычки.

2. Запускайте приложение через `RCynQ.exe` / `RCynQ.sh` или создайте ярлык на них и закрепите его в меню «Пуск» или на рабочем столе.
3. Для CLI добавьте каталог `cli` в `PATH`.
4. На Linux и macOS проверьте права на запуск (скрипт публикации их выставляет):

   ```bash
   chmod +x ~/RCynQ/ui/RCynQ.UI ~/RCynQ/service/RCynQ.Service ~/RCynQ/cli/rcynq
   ```

### 3.3. Первый запуск

1. Запустите приложение ярлыком `RCynQ`.
2. Если конфигурации ещё нет, откроется окно **«Настройка узла RCynQ»**:
   - идентификатор узла (по умолчанию из имени компьютера) и отображаемое имя;
   - **роль** — Source, Mediator или Dest; под списком показано, что делает выбранная роль;
   - рабочая копия (Source) или путь к репозиторию (Dest); у Mediator пути нет;
   - порт сервиса;
   - общий link-токен (для Source и Dest; кнопка рядом генерирует новый).
3. Нажмите **«Сохранить и запустить»**. Приложение запишет конфигурацию и запустит сервис в выбранной роли.

Для **Mediator** больше ничего запускать не нужно: сервис стартует вместе с приложением, поднимает туннели звеньев и следит за ними, а при закрытии приложения всё останавливается.

**Где лежат настройки и данные.** Дистрибутив портативный: в его корне лежит файл-метка `rcynq.portable`, поэтому всё, что создаёт RCynQ, хранится внутри папки установки:
- `config/syncbridge.json` — настройки узла;
- `data/` — база, ключи (в том числе SSH-ключ узла и `known_hosts`), журналы, резервные копии и временные файлы.

В профиль пользователя и системные временные каталоги RCynQ ничего не пишет. Вне папки остаются только средства ОС, которыми RCynQ пользуется: SSH-сервер с его `authorized_keys` и VPN. Удалите файл `rcynq.portable`, если хотите хранить данные в профиле пользователя.

Файл-метка пустой: важен только факт его наличия. Без него программа считает себя обычной установкой и ищет конфигурацию в профиле пользователя (порядок поиска ниже).

**Перенос и копирование.** Каталоги `config/` и `data/` — это личность узла: `NodeId`, ключ подписи, SSH-ключ, токены, список доверенных соседей и история. Копия каталога вместе с ними даёт второй компьютер с той же личностью, и соседи не смогут отличить узлы друг от друга.
- Новый узел ставьте из чистого пакета или скопируйте каталог без `config/` и `data/`.
- Резервная копия узла — весь каталог при закрытом приложении.
- При первом запуске в `data/installation.json` записывается имя компьютера. Если каталог с данными запущен на компьютере с другим именем, вверху окна появляется предупреждение. Кнопка «Это тот же узел» подтверждает переезд и перезаписывает отметку; для нового узла удалите `config/` и `data/`.

Порядок поиска `syncbridge.json`:
1. аргумент `--config <файл>`;
2. переменная окружения `RCYNQ_CONFIG`;
3. `config/syncbridge.json` портативной установки (если рядом с программой есть `rcynq.portable`);
4. `syncbridge.json` в текущем каталоге, если он существует;
5. файл в профиле пользователя: `%APPDATA%\RCynQ\syncbridge.json` на Windows, `~/.config/RCynQ/syncbridge.json` на Linux.

Точный путь показан в окне настройки.

### 3.4. Как приложение управляет сервисом

- **При запуске** приложение проверяет, отвечает ли сервис на `ListenPort`:
  - если отвечает (например, запущен отдельно как служба), приложение просто подключается к нему и при закрытии его **не** останавливает — в строке состояния написано «используется внешний сервис»;
  - иначе приложение запускает `RCynQ.Service` с той же конфигурацией и ждёт, пока он ответит — в строке состояния «сервис запущен приложением».
- **Смена роли** на вкладке «Роль и узлы» → «Сохранить»: приложение перезапускает сервис и перестраивает вкладки под новую роль.
- **При закрытии** приложение просит сервис корректно остановиться: останавливаются конвейер роли, транспорты (AmneziaWG) и SSH-форварды. Если сервис не завершился за 15 секунд, процесс снимается принудительно.
- **Если приложение аварийно завершилось**, сервис замечает это сам (он получает идентификатор родительского процесса) и в течение нескольких секунд корректно останавливается.
- **Если сервис не запустился**, вверху окна показывается причина и кнопка «Повторить». Ошибки конфигурации открывают окно настройки с текстом ошибки.

Где приложение ищет сервис:
1. `--service-exe <путь>` или переменная `RCYNQ_SERVICE_EXE` (можно указать `.exe` или `RCynQ.Service.dll`);
2. каталог `service/` рядом с каталогом приложения (опубликованная раскладка);
3. каталог самого приложения;
4. сборка разработчика `Sources/Apps/RCynQ.Service/bin/<конфигурация>/net10.0/`.

Сервис, запущенный приложением, работает в каталоге файла конфигурации, поэтому относительные пути в `syncbridge.json` (например, `DataRoot`) считаются от этого каталога.

Параметры подключения UI можно задать явно:

| Аргумент | Переменная окружения | Значение |
|----------|---------------------|----------|
| `--config <файл>` | `RCYNQ_CONFIG` | Путь к `syncbridge.json`. |
| `--service <url>` | `RCYNQ_SERVICE_URL` | Адрес сервиса, например `http://127.0.0.1:18443/`. |
| `--token <значение>` | `RCYNQ_API_TOKEN` | Токен API напрямую. |
| `--token-file <файл>` | `RCYNQ_API_TOKEN_FILE` | Файл с токеном API. |
| `--service-exe <файл>` | `RCYNQ_SERVICE_EXE` | Какой сервис запускать. |

### 3.5. Сервис без графического интерфейса (необязательно)

На сервере без рабочего стола (например, Mediator на VPS) сервис можно запускать как обычное консольное приложение. Код возврата:
- `0` — нормальная остановка;
- `1` — аварийная остановка;
- `2` — ошибка конфигурации (список ошибок печатается в stderr).

**Linux (systemd, пользовательский юнит)** — `~/.config/systemd/user/rcynq.service`:

```ini
[Unit]
Description=RCynQ node service
After=network-online.target

[Service]
ExecStart=/opt/rcynq/service/RCynQ.Service --config %h/.config/RCynQ/syncbridge.json
Restart=on-failure
RestartSec=5
# Токен лучше не хранить в файле:
# Environment=RCYNQ_SyncBridge__LinkToken=...

[Install]
WantedBy=default.target
```

```bash
systemctl --user daemon-reload
systemctl --user enable --now rcynq
loginctl enable-linger "$USER"   # чтобы сервис работал без активного входа
journalctl --user -u rcynq -f
```

**Windows (Планировщик заданий):**

```powershell
$action  = New-ScheduledTaskAction -Execute 'C:\Program Files\RCynQ\service\RCynQ.Service.exe' `
           -Argument "--config `"$env:APPDATA\RCynQ\syncbridge.json`""
$trigger = New-ScheduledTaskTrigger -AtLogOn -User $env:USERNAME
$settings = New-ScheduledTaskSettingsSet -RestartCount 3 -RestartInterval (New-TimeSpan -Minutes 1) -ExecutionTimeLimit 0
Register-ScheduledTask -TaskName 'RCynQ Service' -Action $action -Trigger $trigger -Settings $settings
```

**macOS (launchd)** — `~/Library/LaunchAgents/com.rcynq.service.plist` с `ProgramArguments` = путь к `RCynQ.Service`, `--config`, путь к конфигурации; `RunAtLoad` и `KeepAlive` = `true`.

Проверить, что сервис жив:

```bash
curl http://127.0.0.1:18443/health
# {"status":"ok","role":"Mediator"}
```

При первом старте сервис:
1. создаёт каталог данных;
2. применяет миграции базы;
3. создаёт ключ подписи узла и токен локального API `keys/api.token`;
4. заносит в базу звенья из `Chain`.

## 4. Первичная настройка цепочки

Ниже разобрана типовая топология: **Source → Mediator → Dest**. Если Mediator'а нет, пропустите относящиеся к нему шаги: звено Source сразу указывает на Dest, и наоборот.

Условные адреса в примерах:

| Узел | NodeId | Адрес, по которому к нему подключаются | SSH-пользователь |
|------|--------|----------------------------------------|------------------|
| Source | `source-1` | `10.8.0.3` | `dev` |
| Mediator | `mediator-1` | `203.0.113.4` | `jump` |
| Dest | `dest-1` | `10.8.0.2` | `rcynq` |

### 4.1. Шаг 1. Роль каждого узла

На каждом узле запустите приложение и заполните окно первичной настройки (раздел 3.3):

| Узел | Роль | Путь | Link-токен |
|------|------|------|------------|
| Source | Source | рабочая копия, например `/home/dev/projects/app` | сгенерируйте и скопируйте |
| Mediator | Mediator | — | — |
| Dest | Dest | репозиторий, например `/srv/repos/app` | вставьте тот же, что на Source |

`LinkToken` — **общий секрет Source и Dest**, он должен совпадать на обоих узлах.

Без графики то же самое делают командами:

```bash
rcynq role set source --workdir /home/dev/projects/app --node-id source-1
rcynq role set mediator --node-id mediator-1
rcynq role set dest --repo /srv/repos/app --node-id dest-1
rcynq config validate
```

`LinkToken` при этом задайте в `syncbridge.json` или переменной `RCYNQ_SyncBridge__LinkToken`.

### 4.1a. Как узел принимает подключения

Для Source и Dest выбирается один из двух способов — в окне первичной настройки или на вкладке «Роль и узлы» → «Параметры узла» (`Endpoint.Mode` в `syncbridge.json`):

| Режим | `Endpoint.Mode` | Что нужно на узле | Как до него доходит сосед |
|-------|-----------------|-------------------|---------------------------|
| Через SSH-сервер | `SshTunnel` (по умолчанию) | sshd | SSH-сессия до самого узла (посредники — `-J`), проброс на его loopback `ListenPort`, HTTP |
| Без SSH-сервера | `Direct` | Входящий порт `Endpoint.Port` (по умолчанию `18444`) в брандмауэре | SSH-сессия заканчивается на **последнем посреднике**, проброс оттуда на `host:Endpoint.Port` узла, далее HTTPS с проверкой отпечатка сертификата. Без посредника — HTTPS напрямую, SSH не используется |

```json
"Endpoint": { "Mode": "Direct", "BindAddress": "0.0.0.0", "Port": 18444 }
```

В режиме `Direct`:
- сервис открывает второй слушатель `BindAddress:Port` с самоподписанным сертификатом `data/keys/tls/node.crt` (ключ `node.key`, доступ только владельцу). На этом порту доступны только приём патчей (`/patch/sessions/...`), `POST /git/bundle`, `GET /peer/ping` и `GET /health`, остальной API — `404`; локальный API остаётся на `127.0.0.1:ListenPort` с токеном;
- файл экспорта содержит `endpointMode`, `endpointPort` и `tlsFingerprint` (SHA-256 сертификата). Сосед закрепляет отпечаток при импорте и не примет другой сертификат, даже если его подпишет доверенный центр;
- TLS устанавливается между конечными узлами, посредник пересылает только зашифрованные байты;
- посреднику по-прежнему нужен sshd, а в его `authorized_keys` для ключа противоположного узла пишется `permitopen="<host>:<Endpoint.Port>"` вместо `:22`;
- самому узлу `authorized_keys` не нужен: `rcynq ssh allow` и кнопка в приложении ничего не записывают;
- для отправки своих изменений узлу нужен SSH-клиент (`ssh`) и SSH-ключ — он подключается к посреднику как обычно;
- ветки Git забираются иначе, чем через SSH: Source просит Dest о **git bundle** с недостающими коммитами (`POST /git/bundle` на порт RCynQ, авторизация link-токеном и известным узлом Source). Dest создаёт bundle во временном файле и удаляет его после ответа. Первый pull в папку без репозитория создаёт репозиторий (раздел 5.2).

Посредник в режиме `Direct` работать не может: маршрут через него строится только поверх его sshd, и RCynQ сообщит об этом при отправке.

### 4.2. Шаг 2. SSH-ключи

SSH-ключ узла удобнее всего создать из диалога экспорта кнопкой **«Создать ключ»** (шаг 3). Приложение вызовет `ssh-keygen`, создаст `data/keys/ssh/rcynq_ed25519` без парольной фразы с комментарием `rcynq:<NodeId>`, оставит доступ к нему только владельцу и пропишет путь в `Ssh.IdentityFile`. Публичную часть можно взять из `data/keys/ssh/rcynq_ed25519.pub`. Вручную:

```bash
ssh-keygen -t ed25519 -f ~/RCynQ/data/keys/ssh/rcynq_ed25519 -N "" -C "rcynq:source-1"
```

Если ключ создан вручную в другом месте, укажите его в `Ssh.IdentityFile`.

RCynQ подключается со своим файлом настроек SSH (`data/keys/ssh_config`, передаётся как `ssh -F`), поэтому ключ узла, `known_hosts` узла и режим без вопросов действуют на **каждом** хосте цепочки, включая промежуточные. Личный `~/.ssh/config` RCynQ не читает: псевдонимы хостов, `ProxyJump` и прочие настройки из него на соединения RCynQ не влияют — адрес, порт и пользователя соседа задаёт звено.

Комментарий начинайте с `rcynq:` — по нему диагностика находит ключи RCynQ в `authorized_keys`. Ключ с парольной фразой можно использовать через ssh-agent: RCynQ вызывает `ssh` в режиме `BatchMode=yes` и ничего не спрашивает.

**Разрешения в `authorized_keys` создаются автоматически.** Публичный SSH-ключ из файла экспорта сохраняется при импорте, а затем RCynQ записывает ограниченные строки для соседей, которым нужно подключаться к этому узлу:
- сразу после импорта в приложении и после `rcynq import`;
- кнопкой **«Разрешить подключения узлов»** на вкладке «Роль и узлы»;
- командой `rcynq ssh allow`.

Строки RCynQ помечены комментарием `rcynq:<NodeId>`. Строка ключа, который уже есть в файле, заменяется; остальные строки не трогаются. Файл выбирается так же, как его выбирает OpenSSH:
- `Ssh.AuthorizedKeysPath`, если задан;
- на Windows для членов группы «Администраторы» — `%ProgramData%\ssh\administrators_authorized_keys`. Запись в него требует повышения прав: приложение спрашивает подтверждение и запускает `rcynq ssh allow` через запрос UAC, после записи файлу оставляются права только Administrators и SYSTEM;
- иначе `~/.ssh/authorized_keys` (каталог `0700`, файл `0600` на Linux/macOS).

Mediator записывает строки, только когда импортированы оба конечных узла: разрешение Source указывает на адрес Dest, и наоборот. Если в файле экспорта нет SSH-ключа, приложение называет такой узел; экспортируйте его заново с ключом.

Ниже — какие строки получаются. Их же можно добавить вручную, если автоматическая запись недоступна:

**На Mediator** (`~jump/.ssh/authorized_keys`) — только проброс к следующему узлу, без shell:

```
# ключ Source: разрешён только переход на sshd Dest
restrict,port-forwarding,permitopen="10.8.0.2:22",command="exit 1",no-pty,no-agent-forwarding,no-x11-forwarding ssh-ed25519 AAAA... rcynq:source-1
# ключ Dest: разрешён только переход на sshd Source
restrict,port-forwarding,permitopen="10.8.0.3:22",command="exit 1",no-pty,no-agent-forwarding,no-x11-forwarding ssh-ed25519 AAAA... rcynq:dest-1
```

**На Dest** (`~rcynq/.ssh/authorized_keys`) — ключ Source. Разрешены проброс к локальному endpoint Dest (для патчей) и только `git-upload-pack` одного репозитория (для `git fetch`):

```
restrict,port-forwarding,permitopen="127.0.0.1:18443",command="git-upload-pack '/srv/repos/app'",no-pty,no-agent-forwarding,no-x11-forwarding ssh-ed25519 AAAA... rcynq:source-1
```

На Windows автоматическая строка для Dest содержит `command="exit 1"` вместо `git-upload-pack`: путь к репозиторию Windows в принудительной команде OpenSSH для Windows ненадёжен.

**На Source** (`~dev/.ssh/authorized_keys`) — ключ Dest, разрешён только проброс к endpoint Source:

```
restrict,port-forwarding,permitopen="127.0.0.1:18443",command="exit 1",no-pty,no-agent-forwarding,no-x11-forwarding ssh-ed25519 AAAA... rcynq:dest-1
```

Почему строки такие:
- **`command=`** принудительная команда. Соединения RCynQ для проброса (`ssh -N`) не открывают сессию, поэтому она их не затрагивает. Любая попытка выполнить что-то другое запустит только эту команду.
- **`permitopen`** значение должно совпадать с `ListenPort` узла, на который ведёт проброс.
- **sshd на Mediator и Dest** должен разрешать TCP-проброс: `AllowTcpForwarding yes` или `local`.

Проверьте SSH вручную с Source:

```bash
ssh -i ~/.ssh/rcynq_ed25519 -J jump@203.0.113.4 -N -L 127.0.0.1:19000:127.0.0.1:18443 rcynq@10.8.0.2
# в другом терминале:
curl http://127.0.0.1:19000/health
```

### 4.3. Шаг 3. Экспорт конфигурации с автоопределением

Узлы доверяют друг другу через обмен **публичной** конфигурацией. Закрытые ключи никогда не экспортируются.

1. На вкладке **«Роль и узлы»** нажмите **«Экспортировать конфигурацию»**. Приложение сразу опрашивает систему:
   - **сетевые адреса** всех активных интерфейсов с типом: VPN/туннель, локальная сеть, публичный; loopback и link-local отбрасываются;
   - **открытость SSH-порта**: к каждому адресу выполняется TCP-подключение на порт `sshd` — «SSH отвечает» / «SSH не отвечает»;
   - **порт сервиса RCynQ** на `127.0.0.1`;
   - **SSH-пользователь** — текущий пользователь ОС;
   - **SSH-ключ узла**: `Ssh.IdentityFile`, затем `data/keys/ssh/rcynq_ed25519` (личные ключи из профиля пользователя не используются);
   - **отпечаток ключа хоста sshd** через `ssh-keyscan`.
2. Проверьте предложенные значения. Лучший адрес выбран автоматически: сначала адреса, на которых SSH отвечает, среди них — туннель, затем локальная сеть, затем публичный. Адрес можно выбрать из списка или ввести вручную (например, внешний адрес за NAT). Флажки определяют, попадут ли в файл публичный SSH-ключ и отпечаток ключа хоста.
3. Обратите внимание на предупреждения внизу диалога (sshd не запущен, ключ не найден и т.п.). «Проверить снова» повторяет опрос, «Создать ключ» создаёт SSH-ключ.
4. Нажмите **«Экспортировать»** и сохраните файл, например `dest-1.rcynq.json`.

Проверка открытости порта выполняется с этого же компьютера: она показывает, что `sshd` слушает адрес, но не может проверить файрвол или NAT между узлами.

То же из командной строки:

```bash
rcynq export --auto -o dest-1.rcynq.json          # всё определяется автоматически
rcynq export --auto --host 198.51.100.7 -o dest-1.rcynq.json   # явные значения важнее
```

Файл экспорта содержит `NodeId`, роль, публичный ключ подписи, адрес и SSH-пользователя, SSH-порт, порт endpoint, путь к репозиторию (для Dest), публичный SSH-ключ и отпечаток ключа хоста.

### 4.4. Шаг 4. Импорт на соседних узлах

1. Перенесите файлы на соседние узлы любым доверенным способом. Сверьте отпечаток ключа подписи, например по телефону: подменённый файл даст злоумышленнику право слать патчи.
2. На Source и Dest импортируйте сначала Mediator, затем противоположный конечный узел: **«Роль и узлы» → «Импортировать конфигурацию»** или

   ```bash
   # на Source
   rcynq import mediator-1.rcynq.json
   rcynq import dest-1.rcynq.json
   # на Dest
   rcynq import mediator-1.rcynq.json
   rcynq import source-1.rcynq.json
   ```

Импорт:
- запоминает узел и доверяет его ключу подписи;
- закрепляет отпечаток ключа хоста, если он есть в файле: перед подключением RCynQ находит у хоста ключ с этим отпечатком и оставляет в своём `known_hosts` только его, после чего ssh не примет от этого хоста никакой другой ключ (раздел 8);
- сохраняет публичный SSH-ключ узла и обновляет разрешения в `authorized_keys` (раздел 4.2);
- создаёт звено: Mediator получает позицию меньше `1000` (порт 22), противоположный конечный узел — позицию `1000` и порт его `ListenPort`;
- на Mediator только запоминает узел, звенья к Mediator создаются на Source и Dest.

3. Проверьте порядок звеньев в списке «Узлы цепочки» или командой `rcynq link list`:
   - сначала идут посредники (роль Mediator) по возрастанию `Priority`;
   - последним стоит противоположный конечный узел (для Source — Dest, для Dest — Source).

Звенья можно добавить и вручную: кнопкой «Добавить узел», командой `rcynq link add` (раздел 5.3) или в секции `Chain` файла конфигурации (раздел 6.3).

> Звенья, добавленные через приложение, CLI или импорт, хранятся в базе узла. Звенья из `Chain` в `syncbridge.json` при каждом старте сервиса перезаписывают одноимённые записи в базе. Звено, описанное в файле, удаляйте из файла — иначе оно вернётся после перезапуска.
>
> Звено, записанное вручную (в файле, в приложении или командой `rcynq link add`), задаёт адрес соседа, но не всё, что о нём известно узлу: SSH-ключ соседа, режим его подключения и отпечаток TLS-сертификата приходят только с импортом. Сохранение такого звена их не стирает: значения, которых в звене нет, остаются прежними. Изменить их можно только новым импортом.

### 4.5. Шаг 5. Транспорт (необязательно)

По умолчанию используется **Direct** — обычное SSH-соединение. Если сосед доступен только через VPN AmneziaWG, укажите транспорт при добавлении узла (поле «Транспорт» и путь к `.conf`) или командой:

```bash
rcynq link add --name relay --peer-id mediator-1 --peer-role mediator \
    --host 203.0.113.4 --user jump --remote-port 22 --priority 10 \
    --transport AmneziaWG --fallback Direct \
    --setting configPath=/etc/amnezia/amneziawg/awg0.conf
```

Поведение транспорта:
- Mediator поднимает транспорты своих звеньев при старте сервиса и раз в 30 секунд проверяет состояние, при сбое переключаясь на резервный транспорт.
- Вручную — вкладка «Туннель» или `rcynq transport up|down|status <link>`.
- При остановке сервиса (в том числе при закрытии приложения) все туннели останавливаются.
- Для поднятия туннеля нужны права администратора или root: запускайте приложение с ними либо поднимайте туннель заранее средствами ОС.

### 4.6. Шаг 6. Первый Pull на Source

На Dest должен быть Git-репозиторий хотя бы с одним коммитом и выбранной веткой. Больше ничего готовить не нужно.

1. На **Source**: вкладка «Ветки» → «Pull с DEST», или `rcynq git fetch`. Pull работает, даже если на Source ещё ничего нет: пустая папка станет клоном ветки, выбранной на Dest; папка с файлами, но без Git, станет репозиторием, а её отличия от Dest будут видны как изменения к отправке.
2. Проверьте: вкладка «Синхронизация» показывает «База синхронизации: `<ветка> @ <коммит>`», а `rcynq status` — `Sync base: Git <ветка> @ <коммит>`. На Dest база появляется сама из `HEAD`.

**Папка без Git (запасной режим).** Если рабочая копия на обоих узлах — не Git-репозиторий, создайте ручную базовую копию **один раз**, когда содержимое на Source и Dest **совпадает**: на Source, затем на Dest — вкладка «Синхронизация» → «Создать ручную базовую копию», или `rcynq patch baseline`. Для Git-репозитория эта команда не нужна и отклоняется.

### 4.7. Шаг 7. Проверка

1. На каждом узле откройте вкладку **«Диагностика»** → «Запустить проверку» (или `rcynq diagnostics run`). Проверки должны пройти (`✓`). Для проваленных показывается подсказка; безопасные исправления — создание каталога, запуск транспорта — применяются кнопкой «Исправить» (или `rcynq diagnostics run --fix --yes`).
2. На Source сделайте тестовое изменение и нажмите «Отправить изменения» (или `rcynq patch send`). На Dest файл должен появиться, а в истории патчей — статус «применён».

## 5. Повседневная работа

### 5.1. Приложение

Вкладки в верхней строке. Вкладки, неприменимые к роли узла, **показаны серыми и недоступны**: у Mediator это «Синхронизация» и «Ветки». Пока приложение загружается, показывается заставка с иконкой и описанием текущего шага; главное окно открывается, когда всё готово. Если окно слишком узкое, не поместившиеся справа вкладки переносятся в меню **«…»**. Красная точка на вкладке означает, что там что-то требует внимания. Кнопка ↻ справа обновляет текущую вкладку, а если сервис был недоступен — повторяет его запуск.

| Вкладка | Что на ней |
|---------|------------|
| **Обзор** | Роль, имя узла, время последней синхронизации, состояние звеньев, список проблем с кнопкой «Перейти». |
| **Роль и узлы** | Смена роли и пути (приложение перезапускает сервис), список узлов цепочки со статусами, экспорт с автоопределением и импорт конфигурации, добавление и удаление узла (значок корзины появляется при наведении на строку). |
| **Синхронизация** | База синхронизации (ветка и коммит Git или ручная копия), изменения к отправке — все файлы, отличающиеся от коммита Git, с их числом рядом с заголовком; уже полученные соседом помечены «отправлено» и остаются в списке, пока изменение не закоммичено, — кнопка «Отправить изменения» (отправляет все файлы списка, полученные соседом — повторно, он принимает их без конфликта), кнопка «Выбрать файлы» (показывает галочки, чтобы отправить только отмеченные; повторное нажатие скрывает их, и уходят все файлы), история патчей, просмотр diff, кнопка «Разрешить» для конфликтов. Одинаково на Source и Dest. |
| **Туннель** | Звенья, текущий и резервный транспорт, статус и под ним — что именно показала проверка; кнопки «поднять» и «остановить» для не-Direct транспортов. Как проверяется каждое звено — ниже, в «Статус звеньев». |
| **Диагностика** | «Запустить проверку», результаты с подсказками, кнопка «Исправить» для безопасных исправлений (после подтверждения). |
| **Ветки** | Текущая ветка. На Source — расхождение с Dest, `Fetch` (узнать состояние веток Dest, рабочие файлы не меняются) и `Pull с DEST` (скачать ветку Dest в рабочую копию). На Dest — только текущее состояние. |
| **Логи** | Журнал сервиса с фильтром по уровню и экспортом в файл. |
| **Настройки** | Язык интерфейса: список с флагом и названием языка (Русский, English). При первом запуске язык выбирается по языку операционной системы и запоминается в `config/ui-settings.json`; сообщения об ошибках и результаты диагностики выводятся на выбранном языке. Кнопка **«Очистить данные»** удаляет накопленные завершённые данные узла (раздел 7, «Очистка данных»). |

Внизу окна — строка состояния: подписка на события сервиса (зелёная точка — обновления приходят сами) и режим сервиса («сервис запущен приложением» или «используется внешний сервис»).

#### Статус звеньев

Статус звена показывает разное для соседа и для дальнего узла:

- **Сосед** (посредник; для Mediator — оба его звена) проверяется напрямую: открывается ли его порт — sshd, а у узла без SSH-сервера его TLS-порт.
- **Противоположный конечный узел** (Dest для Source и наоборот) напрямую недоступен по самой схеме, поэтому проверяется **пингом по цепочке** — тем же путём, каким идёт патч: SSH через посредника с проверкой ключей хоста, а для узла без SSH-сервера ещё и TLS с закреплённым сертификатом. Тот узел отвечает, только если принял бы от этого узла патч: совпал токен звена и отправитель ему известен. «Онлайн» здесь значит «готов к обмену», а не «порт открыт».

Под статусом на вкладке «Туннель» написано, что показала проверка:

| Что видно | Что это значит |
|-----------|----------------|
| «ожидание», «Проверяется связь с … по цепочке…» | Пинг запущен, результат появится сам через несколько секунд. |
| «онлайн», «… отвечает через … и готов к обмену» | Путь работает, узел примет патч. |
| «недоступно», «Нет пути до …» | Не открылся путь: посредник не отвечает, отклонил ключ узла или у него не тот ключ хоста. Причина — в сообщении. |
| «недоступно», «Путь до … открыт, но его сервис не отвечает» | До машины дошли, но RCynQ на ней не запущен или слушает другой порт. |
| «недоступно», «… отвечает, но не принимает этот узел» | Узел на связи, но отказал: не совпал токен звена или этот узел там не импортирован. Причина — в сообщении. |
| «деградация», «… доступен, но его версия не умеет подтверждать готовность» | На том узле старая версия RCynQ: путь работает, обмен возможен, обновите тот узел. |

Если тот узел сам недавно обращался к этому, в сообщении добавлено «Он обращался к этому узлу в …» — это вторая половина обмена: путь оттуда сюда тоже работает.

Пинг выполняется только по запросу — когда открыта вкладка со звеньями или нажато «Обновить», — а результат держится 30 секунд, чтобы не открывать SSH-соединение на каждый взгляд. Фоновых проверок нет. То же самое, но с ожиданием ответа, делают проверка `CounterpartReachability` на вкладке «Диагностика» и команда `rcynq transport status`.

### 5.2. Сценарии

**Отправить изменения** (Source → Dest или Dest → Source): «Синхронизация» → «Отправить изменения», или

```bash
rcynq status          # что изменилось
rcynq patch send      # собрать и отправить патч
```

Отправка выполняется вручную. После успешного применения на другой стороне отправленные файлы попадают в базы синхронизации обоих узлов: отправитель больше не предлагает их, получатель не отправляет их обратно, даже пока они не закоммичены на Dest.

**Принять изменения.** Входящие патчи применяются сервисом автоматически, если не пересекаются с локальными правками. Статусы патча:

| Статус | Значение |
|--------|----------|
| `Applied` | Применён целиком. |
| `ConflictPending` | Файлы изменены на обеих сторонах; ничего не записано, нужно решение. |
| `Rejected` | Отклонён пользователем (оставлено локальное состояние). |
| `ConflictResolved` | Конфликт разрешён. |
| `Failed` | Ошибка применения (подробности в `patch list` и логах). |

**Разрешить конфликт.** «Синхронизация» → «Разрешить» у патча, или `rcynq patch resolve <patchId> --policy <политика>`:

| Политика | Результат |
|----------|-----------|
| `KeepLocal` | Патч отклоняется, рабочая копия не меняется. Локальная версия файла остаётся в изменениях к отправке: следующая отправка передаст её соседу без нового конфликта. |
| `ApplyIncomingOverLocal` | Конфликтующие файлы копируются в `backups/` каталога данных и перезаписываются входящими. |
| `UseGit` | Трёхстороннее слияние каждого файла (`git merge-file`): общая основа — база синхронизации, одна сторона — локальный файл, другая — входящий. Правки в разных местах файла объединяются. Где обе стороны изменили одни и те же строки, в файле остаются обычные маркеры конфликта (`<<<<<<< local … ======= … >>>>>>> incoming`) — такой файл назван в сообщении, его нужно поправить в редакторе. Локальные версии перед слиянием копируются в `backups/`. Окончания строк берутся из локального файла. Патч после слияния считается разрешённым. Если какой-то файл Git слить не может (двоичный изменён с обеих сторон; у одной стороны удалён, у другой изменён), не меняется ничего, а в окне конфликта названы эти файлы и причина — тогда выберите одну из двух других политик. Репозиторий и чистая рабочая копия для слияния не нужны. |

**Получить ветки с Dest** (только Source): вкладка «Ветки» → «Fetch» или «Pull с DEST», или `rcynq git fetch`. Ветки попадают в `refs/remotes/dest/*`. Fetch только узнаёт состояние веток Dest: рабочие файлы и база синхронизации не меняются, поэтому новые коммиты Dest не выглядят как изменения к отправке. Pull выполняет fetch и **только fast-forward** текущей ветки, затем пересобирает базу синхронизации из нового коммита. Push в Dest не выполняется никогда.

**Pull и локальные изменения.** Pull не требует чистого рабочего дерева. Если файл, который обновляет Pull, изменён локально:

- правка уже доставлена на Dest патчем (или совпадает с версией в новом коммите Dest) — Pull молча заменяет файл версией из Dest и сообщает об этом в выводе. Так после «отправил → Dest закоммитил → Pull» ничего не нужно откатывать вручную;
- правка ещё **не отправлена** на Dest — Pull ничего не меняет и выводит список таких файлов. Отправьте их на вкладке «Синхронизация» (или откатите) и повторите Pull.

Локальные изменения в файлах, которых Pull не касается, остаются как есть.

**Переключение на другую ветку Dest.** Каждый fetch/pull приносит **все** ветки Dest, а не только ту, что сейчас активна там, — просто как `refs/remotes/dest/<имя>`, без своей локальной ветки. «Pull с DEST» синхронизирует только ту ветку, что сейчас выбрана у вас на Source, с одноимённой на Dest; он не подстраивается под то, что сейчас активно на Dest. Чтобы получать другую ветку, переключитесь на неё сами:

```bash
git checkout <ветка>              # если Git находит её среди веток dest сам
git checkout -b <ветка> dest/<ветка>   # если предыдущая команда не сработала
```

Для этого RCynQ держит в `.git/config` репозитория запись `remote "dest"` с заглушкой вместо адреса — она нужна только для того, чтобы обычный Git и IDE (VS Code, GitLens) видели `dest/<ветка>` как «ветку удалённого репозитория» и умели сами создавать по ней локальную ветку (в том числе через `--track`, которым пользуется VS Code). RCynQ никогда не выкачивает через эту запись: реальная передача идёт своим путём (SSH-туннель или bundle через порт RCynQ), поэтому `git fetch dest` или `git pull` из этой записи всегда завершатся ошибкой — это ожидаемо, не пытайтесь чинить её URL, пользуйтесь «Pull с DEST».

Первый Pull одинаково работает через SSH и через bundle:

- в **пустую папку** приходит весь репозиторий с историей, и папка становится клоном (выбирается ветка, выбранная на Dest);
- в папку с **файлами, но без репозитория**, репозиторий создаётся, ветка принимается, а файлы остаются как есть: их отличия от Dest видны как изменения к отправке и не теряются;
- репозиторий, который отстаёт от Dest, получает только новые коммиты; если истории разошлись, «Ветки» показывает «впереди / позади», сливать RCynQ не будет.

**Окончания строк.** RCynQ работает с файлами так же, как ваш Git: с вашими `core.autocrlf` и `.gitattributes`. Изменениями к отправке считаются только файлы, которые сам Git видит изменёнными (как в `git status`) относительно общего коммита, плюс файлы, переданные патчами. Разница CRLF/LF изменением не считается ни в списке к отправке, ни при проверке конфликтов, ни при Pull, поэтому узлы с разными настройками окончаний строк (например, Windows и Linux) не видят ложных изменений и конфликтов. Передаются при этом точные байты файла; если нужно, чтобы на обоих узлах были одинаковые окончания строк, задайте их в `.gitattributes` (например, `* text=auto eol=lf`).

Если Dest работает **без SSH-сервера**, ветки приходят через bundle: Source сообщает, какие коммиты у него уже есть (HEAD, локальные ветки и `refs/remotes/dest/*`), а Dest отдаёт только недостающее.

На Dest в папке репозитория должна быть выбрана ветка (не detached HEAD) и установлен Git; на Source Git тоже нужен.

**Сменить роль узла:** «Роль и узлы» → выбрать роль → «Сохранить». Приложение перезапустит сервис в новой роли. Через CLI: `rcynq role set <роль>`, затем перезапуск приложения или сервиса.

## 6. Справочник конфигурации

### 6.1. Источники и приоритет

Сервис читает настройки из трёх источников. Каждый следующий переопределяет предыдущий:

1. Файл `syncbridge.json` (порядок поиска — раздел 3.3). В файле допускаются комментарии `//`.
2. Переменные окружения с префиксом `RCYNQ_`. Уровни вложенности разделяются двойным подчёркиванием:
   ```
   RCYNQ_SyncBridge__LinkToken=...
   RCYNQ_SyncBridge__ListenPort=18444
   RCYNQ_SyncBridge__Chain__0__Host=203.0.113.4
   ```
3. Аргументы командной строки: `--SyncBridge:ListenPort=18444`.

При ошибке конфигурации сервис не стартует: приложение показывает окно настройки с текстом ошибки, CLI — `rcynq config validate`.

### 6.2. Раздел `SyncBridge`

| Параметр | Тип / по умолчанию | Описание |
|----------|--------------------|----------|
| `NodeId` | строка, **обязателен** | Уникальный идентификатор узла: латинские буквы, цифры, `-`, `_`, `.`, до 128 символов. Не меняйте после обмена конфигурациями. |
| `Name` | строка / `NodeId` | Отображаемое имя. |
| `Role` | `Source` \| `Mediator` \| `Dest`, `Source` | Роль узла. |
| `RepoPath` | путь | Репозиторий Dest. **Обязателен для Dest.** |
| `WorkdirPath` | путь | Рабочая копия Source. **Обязателен для Source**; для Dest необязателен (по умолчанию `RepoPath`). |
| `ListenPort` | 1–65535, `18443` | Порт сервиса на `127.0.0.1`: приём патчей, API, события приложения. |
| `LinkToken` | строка | Общий секрет Source и Dest, передаётся в заголовке `X-Link-Token`. Без токена входящие патчи отклоняются. Лучше передавать через `RCYNQ_SyncBridge__LinkToken`. |
| `DataRoot` | путь / профиль пользователя | Каталог данных узла (раздел 7). Относительный путь считается от каталога конфигурации (при запуске из приложения) или текущего каталога. |
| `AutoMigrate` | bool, `true` | Применять миграции базы при старте. |
| `ExcludedDirectories` | массив, `bin, obj, .vs, .idea, node_modules` | Имена каталогов, которые не попадают в снимки и патчи. `.git` исключается всегда. Имена из массива **добавляются** к списку по умолчанию, убрать из него имя нельзя. Правила — раздел 6.2а. |
| `RespectGitIgnore` | bool, `true` | Не брать в снимки и патчи файлы и папки, описанные в `.gitignore` внутри рабочей папки (вложенные тоже). Правила — раздел 6.2а. |
| `PatchMaxAgeMinutes` | целое, `1440` | Максимальный возраст принимаемого патча в минутах. Допустимое расхождение часов — 5 минут. |
| `RetentionDays` | целое, `10` | Сколько дней хранятся завершённые данные: записи патчей с их diff и содержимым, история, прогоны диагностики и резервные копии перезаписанных файлов. `0` — не удалять по возрасту. Подробнее — раздел 7, «Очистка данных». |
| `Ssh` | объект | Настройки SSH (6.4). |
| `Chain` | массив | Звенья цепочки (6.3). |

### 6.2а. Что не отправляется: `.gitignore`, `ExcludedDirectories` и размер проекта

В патч, в снимки и в базовую копию не попадает всё, что описано двумя механизмами. Они действуют вместе.

**1. Файлы `.gitignore`** (параметр `RespectGitIgnore`, по умолчанию `true`). Узел читает файлы `.gitignore` внутри рабочей папки, в том числе вложенные, и не берёт то, что они описывают. Читает сам, вызывать `git` для этого не нужно, поэтому правило работает и на узле, где нет папки `.git` (например, на Source, куда проект пришёл только файлами).

| Что поддерживается | Как |
|--------------------|-----|
| Пустые строки и комментарии | `# ...` |
| Маски | `*`, `?`, классы `[abc]`, `[!abc]`; `*` не пересекает `/` |
| Папки | `build/` (только папки) |
| Привязка к папке файла | `/name` или шаблон со `/` внутри (`docs/*.md`): считается от папки, где лежит `.gitignore` |
| Шаблон без `/` | Ищется по имени на любой глубине (`*.log`) |
| `**` | `**/temp`, `logs/**`, `a/**/b` |
| Отрицание | `!keep.log` возвращает файл. Внутрь игнорируемой папки вернуть файл нельзя (как в Git) |
| Вложенные `.gitignore` | Более глубокий файл главнее, внутри файла главнее последняя строка |
| Экранирование | `\#name`, `\!name`, `name\ ` (пробел в конце) |
| Регистр | Не различается на Windows и macOS, различается на Linux (как по умолчанию у Git) |

Что **не** читается: `.git/info/exclude` и глобальный файл игнорирования Git (`core.excludesFile`). Это настройки конкретного компьютера, у соседа они другие, поэтому они не могут решать, что входит в общий патч. Если нужно скрыть что-то только у себя, положите правило в `.gitignore` проекта или в `ExcludedDirectories`.

Важно знать:

- **Игнорируется всё, что подпадает под правило, даже если файл уже добавлен в Git.** Правило работает по описанию, а не по индексу Git.
- Сам файл `.gitignore` отправляется как обычный файл, поэтому правила приезжают на соседний узел вместе с проектом.
- Правила берутся из рабочей папки, а базовая копия читается по тем же правилам. Если добавить в `.gitignore` строку `dist/`, папка `dist` просто перестаёт синхронизироваться: соседу не уходит команда её удалить.
- Если правило убрать, файлы, которые оно скрывало, при следующей отправке уйдут как новые.
- Отключить механизм можно параметром `"RespectGitIgnore": false`.

**2. `ExcludedDirectories`** остаётся: список имён папок, которые нужны, когда `.gitignore` их не описывает (или его нет). В окне программы этой настройки нет, только `syncbridge.json`.

| Правило | Пример |
|---------|--------|
| В списке — **имена папок**, а не пути. Папка исключается **на любой глубине** | `"packages"` исключит и `C:\proj\packages`, и `C:\proj\src\lib\packages` |
| Регистр не важен | `"Bin"` = `"bin"` |
| Нельзя: пути (`src/lib`), маски (`*.zip`, `build*`), имена файлов | Для масок и файлов используйте `.gitignore` |
| Папка `.git` исключена всегда | Добавлять не нужно |
| Массив в файле **дополняет** список по умолчанию, а не заменяет | Достаточно вписать свои папки; `bin`, `obj`, `.vs`, `.idea`, `node_modules` исключены всегда, и вернуть их в синхронизацию этим параметром нельзя |

Как изменить: закройте программу на узле, откройте `config\syncbridge.json` и добавьте строку внутри раздела `SyncBridge`:

```json
{
  "SyncBridge": {
    "NodeId": "dest-1",
    "RespectGitIgnore": true,
    "ExcludedDirectories": [ "bin", "obj", ".vs", ".idea", "node_modules", "Backups" ]
  }
}
```

Между строками нужны запятые. Сохраните файл и запустите программу; ошибку в файле программа покажет в окне настройки.

**Менять правила можно и после базовой копии.** Оба механизма действуют и на рабочую папку, и на базовую копию, поэтому скрытые файлы исчезают из обеих сразу и не превращаются в «удалённые».

**Размер проекта.** Патч передаётся не одним документом, а файл за файлом (раздел 1, «Как ходят изменения»). Поэтому проект в сотни мегабайт передаётся за одну отправку, а предел один: **файл не больше 500 МБ**. При превышении отправка останавливается до передачи и называет файл; такой файл исключите правилом `.gitignore` или уберите из проекта. Ошибка `The JSON value of length … is too large`, о которой писали раньше, в этой версии невозможна.

Полезные детали:

- Каждый файл сжимается gzip прямо во время отправки. Уже сжатые файлы (`.zip`, `.png`) от этого почти не уменьшаются.
- Отправитель ждёт ответ на **каждый** запрос не дольше 5 минут (`RequestTimeout`), а не на весь патч.
- Файл, который изменили между сборкой списка и отправкой, приёмник не примет: его хэш не совпадёт с подписанным. Отправка остановится с ошибкой, ничего не применится, повторите отправку.
- Пока патч в пути, правки пользователя не теряются: файл, изменённый после сборки списка, остаётся «изменённым» и уйдёт со следующим патчем.
- Загруженные, но ещё не применённые файлы лежат в `data\patches\uploads`. Неиспользованные удаляются автоматически спустя `PatchMaxAgeMinutes`.
- **Обе стороны должны быть одной версии.** Узел старой версии не знает маршрутов сессии; отправитель скажет об этом в ошибке: «на нём более старая версия RCynQ».

Как найти самые тяжёлые места проекта (PowerShell, подставьте путь):

```powershell
Get-ChildItem C:\proj -Recurse -File -Force -ErrorAction SilentlyContinue |
  Where-Object { $_.FullName -notmatch '\\\.git\\' } |
  Sort-Object Length -Descending | Select-Object -First 20 FullName, @{ n = 'МБ'; e = { [math]::Round($_.Length / 1MB, 1) } }
```

### 6.3. Звено `Chain[]`

| Параметр | Тип / по умолчанию | Описание |
|----------|--------------------|----------|
| `Name` | строка, **обязателен** | Уникальное имя звена. Из него вычисляется стабильный `Id`, если тот не задан. |
| `Id` | GUID | Явный идентификатор звена (необязательно). |
| `PeerNodeId` | строка, **обязателен** | `NodeId` соседа. |
| `PeerName` | строка / `PeerNodeId` | Отображаемое имя соседа. |
| `PeerRole` | `Source` \| `Mediator` \| `Dest`, `Dest` | Роль соседа. |
| `Host` | строка, **обязателен** | Адрес sshd соседа (имя или IP). Значения, начинающиеся с `-`, запрещены. |
| `SshPort` | целое, `22` | Порт sshd соседа. |
| `SshUser` | строка, **обязателен** | Пользователь SSH на соседе. |
| `HostKeyFingerprint` | строка | Отпечаток ключа хоста (`SHA256:...`), любого типа (Ed25519, RSA, ECDSA). Заполняется импортом, если сосед экспортировал его. К хосту, у которого нет ключа с таким отпечатком, RCynQ не подключается. Пусто — ключ принимается при первом подключении без сверки. |
| `SigningPublicKey` | Base64 | Публичный ключ подписи соседа (заполняется импортом). Нужен для конечного узла. |
| `GitRepoPath` | путь | Путь к репозиторию на Dest — для `git fetch` с Source. |
| `RemotePort` | целое, `18443` | Для конечного узла — его `ListenPort`; для Mediator — `22`. |
| `LocalPort` | целое, `0` | Локальный порт SSH-форварда; `0` — выбирается свободный. |
| `Priority` | целое, `0` | Позиция в цепочке: меньше — ближе к этому узлу. Конечный узел должен иметь наибольшую позицию (импорт ставит `1000`). |
| `Transport` | `Direct` \| `AmneziaWG`, `Direct` | Основной транспорт. |
| `FallbackTransports` | массив | Резервные транспорты по порядку. |
| `TransportSettings` | объект строк | Настройки транспорта. Для AmneziaWG: `configPath` — путь к `.conf` туннеля. |

Правила цепочки для Source и Dest:
- все звенья, кроме последнего, ведут на Mediator;
- последнее звено ведёт на противоположный конечный узел.

У Mediator ограничений порядка нет: его звенья описывают соседей, чьи транспорты он поднимает и проверяет.

### 6.4. Раздел `SyncBridge.Ssh`

| Параметр | По умолчанию | Описание |
|----------|--------------|----------|
| `IdentityFile` | стандартные ключи ssh | Закрытый ключ (`IdentitiesOnly=yes`), используется на каждом хосте цепочки. Заполняется кнопкой «Создать ключ». |
| `ConnectTimeoutSeconds` | `10` | Таймаут подключения. |
| `SshExecutable` | `ssh` | Путь к `ssh`. |
| `SshKeygenExecutable` | `ssh-keygen` | Путь к `ssh-keygen`. |
| `SshKeyscanExecutable` | `ssh-keyscan` | Путь к `ssh-keyscan`. |

| `KnownHostsFile` | `data/keys/known_hosts` | Ключи хостов соседей для соединений RCynQ, в том числе промежуточных; личный `~/.ssh/known_hosts` не используется. |
| `ConfigFile` | `data/keys/ssh_config` | Файл настроек SSH, который RCynQ записывает сам и передаёт каждому соединению (`ssh -F`). Правки в нём перезаписываются. Каталог любой, имя файла — только латинские буквы, цифры, `.`, `_`, `-`. |
| `LocalSshdPort` | `22` | Порт локального sshd: проверяется диагностикой и экспортом. |

## 7. Данные узла, резервное копирование, обновление

### Где лежат данные

Если `DataRoot` не задан, данные лежат в каталоге `data/` портативной установки — рядом с файлом `rcynq.portable`. Относительный `DataRoot` считается от каталога файла конфигурации.

Без метки `rcynq.portable` (например, при запуске из исходников) используется профиль пользователя:

| ОС | Каталог |
|----|---------|
| Windows | `%LOCALAPPDATA%\RCynQ\<NodeId>\` |
| Linux | `~/.local/share/RCynQ/<NodeId>/` (или `$XDG_DATA_HOME/RCynQ/<NodeId>/`) |
| macOS | `~/Library/Application Support/RCynQ/<NodeId>/` |

Структура каталога:

```
rcynq.db        база SQLite: узлы, звенья, история и метаданные патчей, зашифрованные секреты
keys/           доступ только владельцу (Windows, Linux, macOS)
  api.token       токен локального API для приложения и других локальных клиентов
  secrets.key     ключ шифрования секретов (в том числе закрытого ключа подписи узла)
  ssh/            SSH-ключ узла: rcynq_ed25519 и rcynq_ed25519.pub
  known_hosts     ключи хостов соседей, запомненные SSH
  ssh_config      настройки SSH для соединений RCynQ (записывается автоматически)
tmp/            временные файлы сборки и применения патчей
patches/        содержимое патчей
snapshots/base/ база синхронизации (из коммита Git или ручная копия)
  base.json       откуда взята база и какие файлы переданы соседу после неё
backups/        резервные копии файлов, перезаписанных при разрешении конфликтов
logs/           rcynq-service-YYYYMMDD.log, хранятся 14 дней
```

### Очистка данных

Узел накапливает записи патчей с их diff и содержимым, историю, прогоны диагностики и резервные копии файлов, перезаписанных при разрешении конфликта (`backups/`). Чтобы каталог данных не рос бесконечно, сервис при запуске и затем раз в сутки удаляет всё завершённое, что старше `RetentionDays` дней (по умолчанию 10; `0` отключает удаление по возрасту).

Никогда не удаляются:
- патч, ожидающий решения по конфликту, вместе с его содержимым — сколько бы он ни ждал;
- патч, который ещё может передаваться (незавершённый, моложе суток);
- последняя запись о базе синхронизации.

Очистить данные немедленно, не дожидаясь срока, можно кнопкой **«Очистить данные»** на вкладке «Настройки» или командой `rcynq data cleanup`. Ручная очистка удаляет всё завершённое независимо от возраста, включая резервные копии; приложение спрашивает подтверждение.

Заодно удаляются временные остатки: файлы в `tmp/` старше часа и каталоги `.rcynq-apply-*` в рабочей папке и в базе синхронизации, оставшиеся от применения патча, прерванного аварийным завершением процесса.

### Резервное копирование

Закройте приложение (или остановите сервис) и скопируйте **целиком** каталог данных и `syncbridge.json`:
- `rcynq.db` и `keys/secrets.key` восстанавливаются только вместе;
- без `secrets.key` закрытый ключ подписи не расшифровать.

Если ключ подписи потерян, удалите каталог данных, запустите приложение заново и повторите экспорт и импорт на соседях. База синхронизации Git-репозитория построится заново сама; для папки без Git создайте ручную базовую копию.

### Обновление

1. Закройте приложение (сервис остановится вместе с ним) или остановите отдельно запущенный сервис.
2. Замените каталоги программ новой сборкой. `syncbridge.json` и каталог данных не трогайте.
3. Запустите приложение — миграции применятся автоматически.

> **Обновляйте оба узла до одной версии.** Формат передачи патча изменился: теперь патч уходит сессией, файл за файлом, а не одним документом. Узел старой версии не понимает нового и наоборот; отправитель сообщит об этом ошибкой «на нём более старая версия RCynQ».

Если `AutoMigrate` = `false`, перед запуском примените миграции вручную:

```bash
RCynQ.Dbs.SQLite.DbMigrator --database <DataRoot>/rcynq.db
RCynQ.Dbs.SQLite.DbMigrator --database <DataRoot>/rcynq.db --list   # применённые версии
```

Мигратор также принимает `--connection "<строка подключения SQLite>"`. Коды возврата: `0` — успех, `1` — ошибка миграции, `2` — неверные аргументы.

## 8. Безопасность

- **Сеть.** Сервис слушает только `127.0.0.1`. Соседи попадают на него исключительно через SSH-форвард.
- **Локальный API.** Все маршруты, кроме `GET /health`, маршрутов сессии передачи (`/patch/sessions/...`), `POST /git/bundle` и `GET /peer/ping`, требуют токен из `keys/api.token`, в том числе автоопределение окружения, генерация ключа и остановка сервиса. Сосед, пришедший через SSH-форвард, этот файл прочитать не может, поэтому управлять узлом не может.
- **Приём патча** (сессия `/patch/sessions`). Манифест патча должен пройти все проверки, а содержимое каждого файла принимается, только если его размер и хэш SHA-256 совпадают с подписанным манифестом; распаковка ограничена объявленным размером, поэтому маленький запрос не может раздуться в огромный файл:
  - верный `LinkToken`;
  - известный отправитель, совпадающий с подписью;
  - получатель — именно этот узел;
  - валидная подпись ECDSA P-256;
  - патч не старше `PatchMaxAgeMinutes` и не повторный;
  - роль узла допускает приём патчей.
- **Пути в патчах.** Запрещены пути внутрь `.git`, выход за корень рабочей копии (в том числе через `..` и символьные ссылки) и абсолютные пути.
- **SSH.**
  - Параметры: `BatchMode=yes`, `StrictHostKeyChecking=accept-new`, `--` перед адресом.
  - Параметры, ключ узла и `known_hosts` узла записаны в собственный файл настроек (`keys/ssh_config`) и действуют на каждом хосте цепочки. Личные `~/.ssh/config`, `~/.ssh/known_hosts` и, если задан `Ssh.IdentityFile`, личные ключи пользователя не используются ни на одном переходе.
  - Адреса и пользователи, похожие на опции ssh, отклоняются.
  - Отпечаток ключа хоста из файла экспорта закрепляется при импорте. Перед подключением RCynQ спрашивает у хоста его ключи по одному типу за раз — соединением, в котором никто не входит в систему и ничего не передаётся, — и находит ключ с закреплённым отпечатком. Этот ключ записывается в `keys/known_hosts` как единственный ключ хоста; дальше ssh сам запрашивает именно его и отклоняет любой другой. Так проверяется каждый хост цепочки, включая промежуточные (хост за посредником опрашивается через посредника). Если ключа с закреплённым отпечатком у хоста нет, подключения не происходит, а в сообщении показаны закреплённый отпечаток и ключи, которые хост предъявил. Тип закреплённого ключа значения не имеет: экспорт прежних версий закреплял RSA-ключ, нынешний — Ed25519.
  - У звена без отпечатка (сосед экспортирован без него или звено записано вручную) ключ принимается при первом подключении без сверки — как в обычном ssh.
  - Git вызывается с ограниченным набором протоколов.
- **authorized_keys.** Используйте только ограниченные строки из раздела 4.2. Диагностика `AuthorizedKeysFormat` сообщает о неограниченных ключах с комментарием `rcynq:`.
- **Секреты.**
  - Закрытый ключ подписи хранится в базе, зашифрованным AES-GCM ключом `keys/secrets.key`.
  - `LinkToken` не храните в репозиториях и общих каталогах; предпочтительна переменная окружения.
- **Экспорт.** Файлы экспорта содержат только публичные данные, но подмена файла равна выдаче доверия. Передавайте файлы по доверенному каналу и сверяйте отпечатки.
- **Автоопределение** выполняется только локально: адреса интерфейсов, TCP-подключения к своим адресам, `ssh-keyscan` к `127.0.0.1`. Никакие внешние сервисы не опрашиваются.

## 9. Диагностика и устранение неполадок

### 9.1. Проверки на вкладке «Диагностика»

| Проверка | Роли | Что проверяет |
|----------|------|---------------|
| `ChainLinkConfig` | все | Звенья корректны, порядок цепочки соответствует роли. |
| `SshClient` | все | Доступен `ssh`. |
| `SshdListening` | все | Локальный sshd слушает `Ssh.LocalSshdPort`. |
| `AuthorizedKeysFormat` | все | `authorized_keys` читается, ключи `rcynq:` ограничены. |
| `NeighborReachability` | все | Доступен sshd ближайшего соседа (у Mediator — всех соседей). |
| `CounterpartReachability` | Source, Dest | Противоположный конечный узел отвечает по всей цепочке и готов к обмену: пинг идёт путём патча, через посредников, с токеном звена. При неудаче сообщает, где оборвалось. |
| `TransportAvailability` | все | Установлены и работают инструменты транспорта звеньев. |
| `GitInstalled`, `GitVersion` | Source, Dest | Git установлен, версия поддерживается. |
| `WorkdirWritable` | Source, Dest | Рабочая копия существует и доступна на запись; можно создать каталог (исправление). |
| `SnapshotIntegrity` | Source, Dest | Базовая копия цела. |
| `PatchEndpointLocal` | Source, Dest | Сервис отвечает на `ListenPort`. |
| `RepoValid` | Dest | `RepoPath` — корректный Git-репозиторий. |

Сервис Dest при старте сам выполняет `GitInstalled`, `GitVersion` и `RepoValid` и пишет результат в журнал.

### 9.2. Причины отклонения патча

Отправитель видит причину в сообщении отправки и в журнале.

| Причина | HTTP | Что делать |
|---------|------|------------|
| `Malformed` | 400 | Патч повреждён или разные версии RCynQ на узлах — обновите обе стороны. |
| `WrongReceiver` | 400 | Последнее звено ведёт не на тот узел — проверьте `PeerNodeId`. |
| `InvalidToken` | 401 | `LinkToken` на Source и Dest различается или не задан. |
| `UnknownSender` | 403 | Получатель не импортировал конфигурацию отправителя. |
| `SenderMismatch`, `InvalidSignature` | 403 | Ключ подписи отправителя изменился (переустановка, потеря данных) — повторите экспорт и импорт. |
| `Replay` | 409 | Патч уже был принят — повторная отправка не нужна. |
| `Expired` | 409 | Патч старше `PatchMaxAgeMinutes` или часы расходятся больше чем на 5 минут — синхронизируйте время (NTP) и отправьте заново. |
| `RoleNotAllowed` | 404 | Патч отправлен на Mediator — исправьте цепочку. |

### 9.3. Частые проблемы

| Симптом | Причина и решение |
|---------|-------------------|
| «Сервис RCynQ недоступен: … actively refused it (127.0.0.1:18443)» / «Подключение не установлено…» | Сервис не запущен. Приложение запускает его само; сообщение означает, что запуск не удался или сервис завершился. Причина показана в верхней панели — нажмите «Повторить». Проверьте, что каталог `service/` лежит рядом с `ui/` (или задан `--service-exe`) и что порт `ListenPort` не занят другой программой. |
| «Не найден RCynQ.Service рядом с приложением» | Нарушена структура каталогов дистрибутива. Верните `service/` рядом с `ui/` или укажите `--service-exe`. |
| Окно настройки открывается с ошибкой | Сервис не принял конфигурацию (код 2). Исправьте поля по тексту ошибки; для правки цепочки используйте `rcynq config validate`. |
| «используется внешний сервис», смена роли не применяется | На порту уже работает сервис, запущенный не приложением (служба, systemd, другой экземпляр). Перезапустите его вручную или остановите и запустите приложение заново. |
| Порт занят при старте | Другой процесс использует `ListenPort` — смените порт в настройке и в `permitopen` у соседей. |
| Экспорт: «SSH-сервер не отвечает» | `sshd` не установлен или не запущен. Windows: `Add-WindowsCapability -Online -Name OpenSSH.Server~~~~0.0.1.0`, `Start-Service sshd`. Linux: `sudo systemctl enable --now ssh`. |
| Экспорт: SSH отвечает только на части адресов | `sshd` слушает не все интерфейсы (`ListenAddress` в `sshd_config`) — выберите адрес, на котором SSH отвечает, или поправьте `sshd_config`. |
| Экспорт: «Не удалось прочитать ключи хоста sshd» | Нет `ssh-keyscan` в `PATH` — установите OpenSSH-клиент или задайте `Ssh.SshKeyscanExecutable`. Экспорт возможен и без отпечатка. |
| `patch send`: ошибка SSH `Permission denied` | Ключ не добавлен в `authorized_keys` соседа или неверный `SshUser` / `IdentityFile`. Проверьте ручной командой из 4.2. |
| `open failed: administratively prohibited` | На Mediator или конечном узле не разрешён проброс: `permitopen` не совпадает с адресом или портом, либо `AllowTcpForwarding no` в `sshd_config`. |
| `Host key verification failed` | Ключ хоста соседа изменился после того, как был записан. Убедитесь, что это легитимно, удалите старую запись (`ssh-keygen -R <host> -f <DataRoot>/keys/known_hosts`) и повторите импорт свежего экспорта соседа. |
| «SSH-ключ хоста узла … не совпадает с закреплённым при импорте» | Хост предъявил не тот ключ, отпечаток которого пришёл в файле экспорта: либо на том узле сменили ключ хоста, либо по этому адресу отвечает другая машина. Соединение закрыто, ничего не отправлено. Если ключ сменили намеренно — экспортируйте конфигурацию того узла заново и импортируйте её здесь. |
| «SSH-ключ хоста узла … не удалось сверить с отпечатком, закреплённым при импорте … хост не предъявил ключ» | До хоста не удалось дойти, чтобы спросить его ключ: он выключен, адрес или порт неверны, либо недоступен посредник перед ним. Причина, которую назвал ssh, приведена в конце сообщения. Проверьте связь (вкладки «Туннель» и «Диагностика») и повторите. |
| В «Изменениях к отправке» лежит то, чего нет в `git status` (например, всё содержимое репозитория) | База синхронизации осталась от старой версии или испорчена. Нажмите **«Пересобрать базу синхронизации»** над списком (или `rcynq patch baseline`) на этом узле: база строится заново из коммита Git, а всё, что запомнено о соседе, сбрасывается. Отправленные, но не закоммиченные на Dest файлы появятся снова; если у соседа файл уже ровно такой, он примется без конфликта. Если в строке состояния написано «используется внешний сервис», сначала перезапустите сам сервис: приложение его не обновляет. |
| «Синхронизация недоступна» / отправка недоступна | Причина написана на вкладке «Синхронизация». На Source чаще всего нужен Pull (репозиторий ещё не получен или текущей ветки нет на Dest). На Dest нужен хотя бы один коммит. Для папки без Git создайте ручную базовую копию на обоих узлах при совпадающих деревьях. |
| «Pull не выполнен … изменения ещё не отправлены на Dest» | Pull защищает неотправленные правки. Отправьте перечисленные файлы на вкладке «Синхронизация» (или откатите их) и повторите Pull. |
| Каждый патч уходит в конфликт | Файл действительно изменён на обеих сторонах: разрешите конфликт (раздел 5.2). Разница только в окончаниях строк конфликтом не считается. Для папки без Git: ручные базовые копии разошлись: приведите деревья к одному состоянию и создайте копию заново на обоих узлах. |
| Туннель AmneziaWG не поднимается | Нет прав или неверный `configPath`. Смотрите вкладку «Туннель», диагностику `TransportAvailability` и журнал. |
| Звено «вернулось» после удаления | Оно описано в `Chain` файла конфигурации — удалите его из файла. |
| `Secret ... could not be decrypted` | `rcynq.db` восстановлен без своего `keys/secrets.key`. Восстановите пару файлов или пересоздайте данные узла (раздел 7). |

Журналы:
- файлы — `<DataRoot>/logs/`;
- в приложении — вкладка «Логи»;
- в консоли сервиса — при отдельном запуске.

## 10. Ограничения

- **Транспорты.** Поддерживаются `Direct` и `AmneziaWG`. Значения `WireGuard`, `OpenConnect` и `Tailscale` зарезервированы и пока не реализованы.
- **Отправка изменений** выполняется вручную. Автоматической отправки по изменению файлов нет.
- **Прерванная передача.** Если отправитель оборвал передачу до последнего шага, у получателя в истории остаётся входящий патч в статусе «ожидает», а загруженные файлы лежат в `datapatchesPloads`. Новая отправка их использует; лишнее удаляется автоматически по истечении `PatchMaxAgeMinutes`.
- **Размер файла.** Один файл может весить не больше 500 МБ (раздел 6.2а). Число и общий размер файлов не ограничены.
- **Git** работает только в сторону Source: fetch и fast-forward pull. Push в Dest не выполняется намеренно.
- **Строки authorized_keys** добавляются вручную (раздел 4.2). Экспорт включает публичный SSH-ключ, но на соседе строку нужно добавить самостоятельно; диагностика проверяет её формат.
- **Проверка портов при экспорте** выполняется с этого же компьютера: файрвол и NAT между узлами она не проверяет. Внешний адрес за NAT введите вручную.
- **Ярлык** хранит абсолютные пути: после переноса каталога дистрибутива его нужно пересоздать.
- **Служба ОС.** Для работы без графики сервис не регистрируется как служба Windows или демон автоматически — используйте примеры из раздела 3.5.
- **Исправление «Перезапустить локальный endpoint»** только проверяет доступность сервиса; перезапуск выполняйте кнопкой «Повторить» в приложении или средствами ОС.
