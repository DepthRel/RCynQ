# Архитектура RCynQ

[English](../En/Architecture.md) · [Deutsch](../De/Architecture.md) · [Español](../Es/Architecture.md) · [Français](../Fr/Architecture.md) · [Português](../Pt/Architecture.md) · **Русский**

## Узлы

Одна программа работает в трёх ролях; роль задаётся в конфигурации.

| Роль | Что это | Что делает |
|---|---|---|
| **Workstation** | Компьютер, за которым вы работаете | Хранит рабочие копии, получает ветки, отправляет и принимает патчи |
| **Origin** | Компьютер с закрытыми репозиториями | Предлагает свои репозитории, принимает и отправляет патчи |
| **Relay** | Компьютер, доступный обоим концам | Пересылает SSH-соединения. Репозитория нет, содержимое не видит |

Цепочка — `Workstation → Relay (один или несколько) → Origin`. Без узла Relay концы соединяются напрямую.

## Правило: репозиторий на Origin только читается

- RCynQ никогда не делает push и не создаёт в Git-репозитории на узле Origin собственных коммитов, remote, настроек и ссылок, не обновляет его индекс (Git запускается с `GIT_OPTIONAL_LOCKS=0`).
- Рабочее дерево и выгруженная ветка на Origin меняются только тем, что прислал пользователь: файлами патча или, если Origin принимает коммиты, собственными коммитами пользователя, до которых ветка перематывается вперёд. Эта перемотка остаётся в reflog ветки, и обычный Git её отменяет.
- Сохранение, применение или удаление файла patch на Origin — собственное действие пользователя на этом узле: оно меняет только файлы рабочей папки. Patch собирается в отдельном индексе и каталоге объектов, поэтому в `.git` ничего не пишется, а то, что добавлено в индекс вручную, там и остаётся.
- Всё, что хранит Origin (список репозиториев, база синхронизации, история, резервные копии, коммиты в ожидании применения), лежит в `syncbridge.json` и в папке данных узла.
- Служебные действия Git (создание репозитория в пустой папке, remote `rcynq`, `refs/remotes/rcynq/*`, быстрый переход вперёд при Pull) выполняются только в рабочей копии на узле Workstation.

Сквозные тесты сравнивают каждый файл в `.git` до и после регистрации, переключения, выдачи и осмотра репозитория, а также до и после доставки коммитов, которая отклонена или ждёт.

## Каналы

Оба канала используют одно соединение и одну авторизацию.

**Git-канал (Origin → Workstation).** Workstation называет репозиторий и коммиты, которые у него уже есть. Origin отвечает инкрементальным Git bundle. Workstation загружает его в `refs/remotes/rcynq/*` и выполняет быстрый переход вперёд. Push не выполняется никогда. Затем Origin перечисляет все свои ветки, и `refs/remotes/rcynq/*` приводится в соответствие с этим списком: bundle несёт только ветки с новыми коммитами, поэтому ветка, созданная на коммите, который уже есть у Workstation, ветка, перемотанная назад, и удалённая ветка приходят этим путём. Pull делает так, что текущая ветка отслеживает `rcynq/<ветка>`: Git сравнивает её с Origin, а не с remote, до которого этот компьютер не дотягивается.

**Канал патчей (в обе стороны).** Патч — это разница между рабочей папкой и *базой синхронизации*, то есть тем, что заведомо есть у соседа. База строится автоматически из общего для узлов коммита Git и уже переданных файлов. Доставка: подписанный манифест, затем каждый файл по его SHA-256, затем фиксация, которая применяет всё или ничего. Конфликт разрешается одним из четырёх способов: оставить локальный файл, принять входящий (с резервной копией), трёхстороннее слияние Git или внешний инструмент слияния, выбранный в настройках (VS Code, Visual Studio, IDE JetBrains, KDiff3, Meld, WinMerge, Beyond Compare, P4Merge, TortoiseGitMerge или любой другой, описанный своей командной строкой). С инструментом слияния правки в разных местах Git сливает сам, файлы с пересекающимися правками по очереди открываются в инструменте, и ничего не записывается, пока не слиты все файлы; слияние, сделанное для локального файла, который тем временем изменился, отклоняется.

**Файлы patch (Workstation и Origin).** Кнопка **Сохранить** на вкладке «Синхронизация» или команда `rcynq patch save <file>` записывает изменённые файлы в обычный файл `.patch`, понятный `git apply`: отмеченные файлы или все, если ничего не отмечено. Patch строится от того коммита, с которым сравнивает вкладка. Если галочка **Сохранить изменения в рабочей ветке** снята или указан `--discard`, изменения убираются обратным применением этого же файла и только после его записи: правки, сделанные позже в других местах, остаются, а на Workstation файлы также уходят из индекса. **Применить patch** на вкладке «Ветки» или `rcynq patch apply <file>` переносит patch в рабочую папку: пользователь выбирает файлы в плоском списке или дереве (`rcynq patch files <file>` перечисляет их, `--path` выбирает), ничего не добавляется в индекс и не коммитится, а результат виден как обычные локальные изменения. Patch либо подходит целиком, либо ничего не меняет, а причина объясняется пользователю. Git отказывает в путях за пределы рабочей папки и внутрь `.git`. Байты идут через API, поэтому пути клиента не попадают в сервис, а каждое использование оставляет запись с SHA-256 файла в журнале сервиса. Сам по себе файл patch не попадает на другой узел: он отправляется как любое другое изменение.

**Доставка коммитов (Workstation → Origin).** Коммиты, подготовленные на Workstation (cherry-pick, слияния), приходят на Origin как есть: те же хэши, авторы и порядок. Workstation отправляет блок своих неотправленных коммитов, начиная с самого старого, — Git bundle с подписанным конвертом; его несёт сессия патча. Origin принимает его, только если пользователь включил **Принимать коммиты с Workstation**, только для выгруженной ветки и только если её `HEAD` — тот коммит, на котором построен блок; иначе сразу отказ. Объекты распаковываются в карантин рядом с репозиторием и сверяются с подписанным списком (цепочка первых родителей, каждый путь, который затрагивает коммит); только после этого pack-файлы переносятся в `.git`, а ветка перематывается вперёд. Если перемотка не удалась, pack-файлы убираются обратно. Пока в рабочем дереве Origin есть изменения, коммиты ждут: пользователь применяет или отклоняет их там, а патчи с файлами в это время не принимаются. После применения Fetch выравнивает Workstation с Origin. Пока ветка стоит прямо на коммите Origin, её коммиты не считаются изменениями к отправке: канал патчей предлагает только незакоммиченное, по-прежнему относительно версии, которая есть на Origin. Workstation откатывает неотправленные коммиты (Soft, Mixed, Hard) только когда в её рабочем дереве нет изменений.

## Как узел принимает подключения

| Режим | Путь | Чем проверяется узел |
|---|---|---|
| SSH-сервер | `ssh -L` на локальный порт узла, узлы Relay — как промежуточные хосты | Закреплённый ключ хоста SSH |
| Собственный TLS-порт (по умолчанию `18444`) | Прямо на порт или через SSH-проброс, который заканчивается на последнем узле Relay | Закреплённый отпечаток сертификата |

Узел Relay всегда работает через свой SSH-сервер. Ключи в `authorized_keys` ограничены одним пробросом порта и не могут выполнять команды.

Локальный API узла слушает только loopback (по умолчанию `18443`) и требует токен из папки данных.

## Маршруты до узла

Узел может быть доступен по нескольким адресам: например, через туннель поверх UDP и через второй туннель поверх TCP. Каждый такой адрес — *маршрут* звена. Ключи и отпечатки узла общие для всех маршрутов, различается только адрес.

- **Хранение.** Маршруты лежат в звене. Адрес узла в звене — всегда адрес используемого маршрута, поэтому патчи, Git-канал, проверка связи и диагностика идут по выбранному маршруту, ничего о маршрутах не зная.
- **Проверка.** Раз в 15 секунд, а при неудачной проверке связи сразу, узел проверяет каждый маршрут. Соседа он проверяет TCP-соединением. Узел за узлами Relay — через SSH-проброс до адреса маршрута: ответом считается баннер SSH-сервера или TLS-рукопожатие.
- **Выбор.** Побеждает отвечающий маршрут с наименьшим приоритетом; среди равных — самый быстрый, если он заметно быстрее используемого. Когда лучший маршрут снова отвечает, узел возвращается на него. Пока не отвечает ни один, узел остаётся на прежнем.
- **Ручной выбор.** Закреплённый маршрут используется, отвечает он или нет, пока выбор не возвращён узлу.

У звена с одним адресом маршрутов нет: оно не проверяется и не меняется, узел работает как раньше.

Путь через несколько узлов Relay задаёт конечный узел: он перечисляет их по порядку и сам проходит по SSH. Узел Relay остаётся пассивным; он лишь разрешает ключам конечных узлов проброс к узлам противоположной роли и к SSH-серверам соседних узлов Relay — по каждому известному ему адресу.

## Приглашения

Узел приглашает соседа одноразовым билетом: это случайный секрет (узел хранит только его SHA-256), роль и срок действия. В приглашении — карточка узла, карточки Relay на пути, билет, link-токен для противоположного узла и билет Relay, если он есть у узла.

- **Через SSH-сервер.** К билету прилагается одноразовый ключ Ed25519. Его строка в `authorized_keys` — `restrict,expiry-time=…,command="rcynq enroll --config …"`: ключ не может запустить ничего, кроме присоединения, а после срока сервер его отвергает. Присоединяющийся узел входит с ним — через Relay как промежуточные хосты — и передаёт свою карточку как команду; `rcynq enroll` отдаёт её службе по loopback. Строка удаляется, как только билет использован, отозван или истёк.
- **Через собственный TLS-порт.** Запрос уходит на `/peer/enroll` этого порта; отпечаток сертификата из приглашения закрепляется.

Пригласивший узел проверяет билет, гасит его за один шаг, импортирует карточку и разрешает ключ. Relay отвечает конечному узлу билетом для противоположного узла, и тот передаёт его дальше в своём приглашении. Ключ хоста или сертификат каждого узла закрепляется по приглашению до того, как что-либо отправлено. Автоматически присоединение идёт не больше чем через один Relay; для более длинного пути нужны файлы.

## Защита обмена

| Защита | Механизм |
|---|---|
| Кто может отправлять | Общий link-токен и известный идентификатор соседа в каждом запросе |
| Целостность и авторство | Подпись ECDSA P-256 над манифестом, включая имя репозитория |
| Повторы | Проверяются идентификатор и возраст патча; патч принимается один раз |
| Выход за пределы папки | Пути в патче канонические и обязаны оставаться внутри рабочей папки |
| Чужой репозиторий | Патч для репозитория, с которым получатель сейчас не работает, отклоняется |
| Раскрытие Origin | Сосед узнаёт только имена репозиториев, но не пути; bundle выдаётся только по зарегистрированному имени |
| Коммиты | Выключено, пока пользователь не разрешит на Origin; ветка, база, каждый коммит и хэш bundle подписаны; объекты лежат в карантине до проверки; только перемотка вперёд выгруженной ветки |
| Присоединение | Одноразовый билет со сроком (хранится только хеш); одноразовый SSH-ключ только для команды присоединения, с `expiry-time`; ключ хоста и сертификат закрепляются по приглашению |

## Репозитории

- Origin ведёт каталог: имя → папка. Имя — от 1 до 64 символов из `A–Z a–z 0–9 . _ -`.
- Workstation хранит соответствие имя → локальная папка и может добавить только имя, которое предлагает Origin.
- Узел работает с одним репозиторием одновременно. Переключение не требует перезапуска: оно ждёт окончания идущей отправки, приёма или Pull и затем меняет рабочую папку сразу для всего.
- Каждый пинг несёт имя репозитория, с которым работает узел, в обе стороны. Узел, узнавший о переключении соседа, сообщает об этом пользователю и сам не переключается.
- База синхронизации ведётся отдельно по каждому репозиторию. История патчей показывается для текущего репозитория.

## Хранение

```
<папка программы>/
  config/syncbridge.json     настройки узла, связи, репозитории
  data/
    rcynq.db                 SQLite: соседи, связи, патчи, история, зашифрованные секреты (ключ подписи)
    keys/                    SSH-ключ, TLS-сертификат, токен API, known_hosts
    patches/  backups/       содержимое патчей и файлы, заменённые патчем
    snapshots/               база синхронизации (по папке на каждый дополнительный репозиторий)
    logs/
```

Файл конфигурации прежней версии преобразуется при запуске; исходный сохраняется как `syncbridge.json.bak`.
