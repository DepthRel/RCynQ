# RCynQ: сценарий «A (Source) — B (Mediator) — C (Dest без SSH)»

Инструкция для конкретной схемы:

- **A (Source)** соединяется с **B (Mediator)** через AmneziaWG. На A и B можно поднять SSH-сервер.
- **B (Mediator)** соединяется с **C (Dest)** через корпоративный VPN.
- На **C (Dest)** SSH-сервер поднять **нельзя**.
- Цель: получить код из репозитория на C на компьютере A.

Общие понятия (роли, экспорт/импорт, link-токен) описаны в [BeginnerSetupGuide.md](BeginnerSetupGuide.md). Здесь — только то, что нужно именно для этой схемы, но от начала до конца.

> **Статус документа.** Всё, что касается настройки RCynQ, сверено с кодом репозитория (маршрутизация `ChainRoute`, `PeerAccessPlanner`, `BaselineService`, `DefaultPatchReceiver`). На реальных трёх машинах сценарий не запускался: этап 9 (первая загрузка кода) — мой вывод из чтения кода, а не описанная в документации возможность. Если что-то поведёт себя иначе — смотрите раздел 14.

## 1. Как это будет работать

```
   AmneziaWG                         корпоративный VPN
┌─────────┐   SSH :22    ┌─────────┐   TCP :18444 (TLS)   ┌─────────┐
│    A    │ ───────────▶ │    B    │ ───────────────────▶ │    C    │
│ Source  │              │Mediator │                      │  Dest   │
│ sshd ✔  │ ◀─────────── │ sshd ✔  │ ◀─────────────────── │ sshd ✘  │
└─────────┘   SSH :22    └─────────┘   SSH :22 (к B)      └─────────┘
                              │
                              └── дальше B пробрасывает на A:22
```

Ключевое: **C не принимает SSH**, поэтому RCynQ на C открывает собственный порт `18444` с шифрованием TLS. Соединения идут так:

| Направление | Кто подключается | Куда | Через что | Что видит B |
|-------------|------------------|------|-----------|-------------|
| A → C (отправка с A) | A запускает `ssh` | на **B:22**, оттуда проброс на **C:18444** | AmneziaWG, затем корпоративный VPN | Только зашифрованные байты. TLS устанавливается между A и C напрямую |
| C → A (**отправка с C — ваша цель**) | C запускает `ssh` | на **B:22** как на «трамплин», оттуда на **A:22**, там проброс на порт RCynQ на A | Корпоративный VPN, затем AmneziaWG | Только зашифрованный SSH-поток. B пробрасывает его и не расшифровывает |

**Главный риск схемы.** Чтобы получить код с C на A, компьютер **C должен сам подключаться к B на порт 22** через корпоративный VPN. Компьютер B в корпоративной сети — VPN-клиент, и во многих организациях подключения *к* VPN-клиентам из корпоративной сети запрещены брандмауэром. Проверьте это в этапе 0, **до** всего остального. Если C не может открыть TCP-соединение к B:22, RCynQ в этой схеме сможет отправлять только A → C, а получать код с C не сможет (RCynQ умеет только «отправить от себя»: режима «забрать у соседа» нет, `git fetch` с C тоже недоступен — он требует SSH на C).

## 2. Допущения

Если что-то из этого у вас иначе — скажите, поправлю инструкцию.

1. **На всех трёх компьютерах Windows 10/11.** Для Linux см. раздел 12 в [BeginnerSetupGuide.md](BeginnerSetupGuide.md).
2. **AmneziaWG (A ↔ B) и корпоративный VPN (B ↔ C) уже настроены вами и работают.** RCynQ их не настраивает: он использует уже готовые адреса. Транспорт звеньев в RCynQ остаётся `Direct` (создаётся при импорте по умолчанию) — **не** включайте `AmneziaWG` в звеньях, это нужно только если RCynQ сам должен поднимать туннель.
3. На **C** есть **SSH-клиент** (`ssh -V` работает — он входит в Windows 10/11 отдельно от SSH-сервера) и разрешено запускать программу из папки `C:\RCynQ`.
4. На **C** можно разрешить входящий TCP-порт `18444` (самому или через ИТ-службу). Это порт RCynQ, а не SSH.
5. **Git** установлен на A и C.
6. Учётные записи на всех трёх — с правами администратора (для записи `administrators_authorized_keys` на A и B).

## 3. Таблица адресов

Скопируйте в блокнот и заполняйте по ходу. Названия отличаются от BeginnerSetupGuide: здесь они говорят, о какой сети речь.

| № | Что | Пример | Ваше значение |
|---|-----|--------|---------------|
| **B_AWG** | Адрес B в сети AmneziaWG (по нему A видит B) | `10.8.1.2` | |
| **B_CORP** | Адрес B в корпоративном VPN (по нему C видит B) | `10.50.7.15` | |
| **C_CORP** | Адрес C, по которому его видит **B** | `10.50.2.20` | |
| **A_AWG** | Адрес A в сети AmneziaWG (по нему B видит A) | `10.8.1.3` | |
| **P_A** | Имя пользователя Windows на A | `dev` | |
| **P_B** | Имя пользователя Windows на B | `office` | |
| **P_C** | Имя пользователя Windows на C | `builder` | |
| **T** | Link-токен (создаётся на C, копируется на A) | длинная строка | |

Как узнать адрес: на компьютере выполните `ipconfig` и найдите адаптер AmneziaWG (или VPN-клиента). **Важно про C_CORP:** это адрес, по которому именно **B** достучится до C. Он может отличаться от адреса, который C показывает у себя (NAT, DNS-имя). Проверяйте его командой с B (этап 0), а не «по ощущениям».

## 4. Этап 0. Проверка сети до установки RCynQ

Проверки делаются встроенной командой `Test-NetConnection` в обычном PowerShell. В ответе нужна строка **`TcpTestSucceeded : True`**. Порты пока закрыты (SSH ещё не поднят), поэтому сейчас проверяем только **маршрутизацию**: `ping` и `tracert`. Реальные проверки портов — в этапе 2 после включения SSH.

### 0.1. Пинг по каждому ребру

| Откуда | Команда | Что ожидать |
|--------|---------|-------------|
| A | `ping <B_AWG>` | Ответы. |
| B | `ping <A_AWG>` | Ответы. Нужно **обязательно**: B будет подключаться к A на порт 22 (проброс C → A) |
| B | `ping <C_CORP>` | Ответы. |
| C | `ping <B_CORP>` | Ответы. Нужно **обязательно** (см. раздел 1: главный риск) |

Некоторые сети запрещают ICMP, тогда `ping` молчит, даже когда TCP работает. Если пинг не проходит, не делайте вывод сразу — вернитесь к проверке портов в этапе 2.

### 0.2. Что делать с результатом

| Результат | Что это значит |
|-----------|----------------|
| Все четыре пинга проходят | Продолжайте. |
| B не видит A (`ping <A_AWG>` с B) | В вашей AmneziaWG сервер не маршрутизирует трафик в сторону A. Настройте сеть AmneziaWG так, чтобы B мог обращаться к A по адресу A_AWG. Без этого не заработает C → A |
| C не видит B (`ping <B_CORP>` с C) | Корпоративная сеть не пропускает C → VPN-клиент B. Решение только на стороне ИТ: попросите разрешить TCP `22` от C_CORP к B_CORP. Без этого получить код с C на A нельзя |
| B не видит C | Проверьте, что VPN на B подключён и адрес C_CORP верный |

## 5. Этап 1. Установка на все три компьютера

Повторите на **A, B и C**.

1. Создайте папку **`C:\RCynQ`** (без пробелов и русских букв; не `C:\Program Files`).
2. Распакуйте `RCynQ-win-x64.zip` и скопируйте **содержимое** вложенной папки `RCynQ` в `C:\RCynQ`. Должно получиться:

   ```
   C:\RCynQ\
     RCynQ.cmd
     rcynq.portable
     cli\  dbmigrator\  service\  ui\
   ```

3. **Не копируйте** папку, где программа уже запускалась (папки `config` и `data` — «личность» узла). Для каждого компьютера берите чистый архив.
4. Запускайте программу файлом **`C:\RCynQ\RCynQ.cmd`**.

Если архива нет, соберите его: `./Scripts/publish-win.ps1` — результат `artifacts\publish\RCynQ-win-x64.zip`.

## 6. Этап 2. SSH-сервер на A и B, порт на C

### 2.1. На A и на B: включить SSH-сервер

PowerShell **от имени администратора**:

```powershell
Add-WindowsCapability -Online -Name OpenSSH.Server~~~~0.0.1.0
Set-Service -Name sshd -StartupType Automatic
Start-Service sshd
Get-Service sshd
```

В колонке `Status` должно быть **`Running`**. Запишите имя пользователя: `$env:USERNAME` → **P_A** (на A) и **P_B** (на B).

Если первая команда завершилась ошибкой `0x800f0954`, см. пункт 0.3 в [BeginnerSetupGuide.md](BeginnerSetupGuide.md) (установка из MSI-пакета Win32-OpenSSH).

Проверьте брандмауэр. На A **и** на B правило sshd должно действовать в сети, в которую попадает адаптер AmneziaWG (Windows часто относит новые адаптеры к профилю «Общедоступная»):

```powershell
Get-NetFirewallRule -Name *ssh* | Format-Table Name, Enabled, Profile, Direction, Action
```

Если у правила в `Profile` не `Any` и есть риск, что VPN-адаптер попал в другой профиль — задайте профиль явно:

```powershell
Set-NetFirewallRule -Name OpenSSH-Server-In-TCP -Profile Any
```

(Имя правила может отличаться: возьмите его из вывода первой команды. Если правила нет, создайте: `New-NetFirewallRule -Name sshd -DisplayName 'OpenSSH Server (sshd)' -Enabled True -Direction Inbound -Protocol TCP -Action Allow -LocalPort 22`.)

### 2.2. На C: SSH-сервер НЕ ставим. Готовим порт и клиент

**Проверьте SSH-клиент** (обычный PowerShell):

```powershell
ssh -V
```

Должна появиться строка вида `OpenSSH_for_Windows_9.5p1`. Если команды нет — «Параметры» → «Приложения» → «Дополнительные компоненты» → «Клиент OpenSSH» или попросите ИТ-службу. SSH-клиент нужен C, чтобы отправлять изменения через B.

**Разрешите входящий порт 18444.** PowerShell **от имени администратора**. Лучше сразу ограничить источник адресом B, каким его видит C (это B_CORP):

```powershell
New-NetFirewallRule -Name rcynq -DisplayName 'RCynQ' -Enabled True -Direction Inbound -Protocol TCP -Action Allow -LocalPort 18444 -RemoteAddress <B_CORP>
```

Если вы не уверены, с какого адреса B приходит на C (NAT), сначала выполните команду без `-RemoteAddress`, а после успешной проверки сузьте правило. Если брандмауэром управляет ИТ-служба, попросите открыть входящий TCP `18444` для адреса B.

> Порт `18444` открывает самодельный TLS-сервер RCynQ с закреплением отпечатка сертификата. Наружу на нём доступны только `POST /patch` и `GET /health`. На корпоративном компьютере такое изменение, вероятно, стоит согласовать с ИТ-безопасностью.

### 2.3. Реальная проверка портов

Порт `18444` на C пока не слушает (программа не запущена), поэтому его проверим позже, в этапе 7. Сейчас проверьте только SSH:

| Откуда | Команда | Ожидание |
|--------|---------|----------|
| A | `Test-NetConnection <B_AWG> -Port 22` | `TcpTestSucceeded : True` |
| B | `Test-NetConnection <A_AWG> -Port 22` | `True` |
| C | `Test-NetConnection <B_CORP> -Port 22` | `True` (**главная проверка схемы**) |

Если любая из них `False`, не идите дальше: смотрите раздел 14.

## 7. Этап 3. Первый запуск и файлы узлов: B

Все действия — на B.

### 3.1. Первый запуск

1. Запустите `C:\RCynQ\RCynQ.cmd`. Откроется окно **«Настройка узла RCynQ»**.
2. Заполните:
   - **Идентификатор узла:** `mediator-1`.
   - **Отображаемое имя:** `Посредник`.
   - **Роль узла:** **Mediator**.
   - **Порт сервиса:** `18443` (по умолчанию).
3. **«Сохранить и запустить»**. Внизу окна: «сервис запущен приложением».

### 3.2. Два файла экспорта

A и C видят B по **разным** адресам, поэтому файлов нужно два.

1. **«Роль и узлы» → «Экспортировать конфигурацию».** Дождитесь опроса адресов. Предупреждение «SSH-ключ узла не найден» для посредника можно игнорировать.
2. Убедитесь, что в строке про SSH-сервер стоит галочка. Если крестик — вернитесь к пункту 2.1.
3. **Файл для A.** Выберите адрес **B_AWG** (если его нет в списке — введите вручную) → «Экспортировать» → сохраните как `mediator-for-a.rcynq.json`.
4. **Файл для C.** Снова «Экспортировать конфигурацию» → выберите/введите адрес **B_CORP** → «Экспортировать» → сохраните как `mediator-for-c.rcynq.json`.

Файлы содержат публичные данные, но подмена файла равна выдаче доверия. Передавайте их по доверенному каналу (рабочая почта, флешка) — не через открытые сервисы.

## 8. Этап 4. Первый запуск и файл узла: C

Все действия — на C.

### 4.1. Первый запуск

1. Запустите `C:\RCynQ\RCynQ.cmd` и заполните окно:
   - **Идентификатор узла:** `dest-1`.
   - **Роль узла:** **Dest**.
   - **Путь к репозиторию:** папка проекта на C (в ней должна быть скрытая папка `.git`).
   - **Общий link-токен:** уже сгенерирован. **Скопируйте его в таблицу, строка T.**
   - **Как соседи подключаются к этому узлу:** **«Без SSH-сервера: собственный порт с TLS»**. Порт `18444`.
2. **«Сохранить и запустить»**.

> Это тот самый выбор, который делает схему возможной. Если выбрать «Через SSH-сервер», A не сможет отправлять на C, а разрешения в `authorized_keys` будут записываться зря.

### 4.2. Проверить, что порт открылся

В **PowerShell на C**:

```powershell
Test-NetConnection 127.0.0.1 -Port 18444
```

Ожидание — `True`. Если `False`: не выбран режим «Без SSH-сервера» либо программа не запущена. Смотрите вкладку «Логи».

### 4.3. Файл экспорта C

1. **«Роль и узлы» → «Экспортировать конфигурацию».**
2. Если написано «SSH-ключ не найден» — нажмите **«Создать ключ»** и подождите пару секунд. Ключ нужен C **обязательно**: им C подключается к B и A.
3. В списке адресов выберите **C_CORP** (адрес, по которому C виден **с B**). Если такого нет в списке или B видит C по другому адресу (NAT, DNS-имя) — введите вручную то, что проверено в этапе 7.
4. Флажок «Включить публичный SSH-ключ узла» — **включён**.
5. Диалог покажет **отпечаток TLS-сертификата** и строку «Узел без SSH-сервера: соседи подключаются к порту RCynQ 18444». Отпечаток попадёт в файл сам.
6. «Экспортировать» → сохраните как `c-dest.rcynq.json`.

## 9. Этап 5. Первый запуск и файл узла: A

Все действия — на A.

### 5.1. Подготовить рабочую папку

Так как цель — получить код с C на A, на A рабочая папка должна быть **пустой** (объяснение — в этапе 9). Создайте, например, `C:\Projects\app` и ничего в неё не кладите.

### 5.2. Первый запуск

1. Запустите `C:\RCynQ\RCynQ.cmd` и заполните окно:
   - **Идентификатор узла:** `source-1`.
   - **Роль узла:** **Source**.
   - **Рабочая копия:** `C:\Projects\app`.
   - **Общий link-токен:** сотрите сгенерированный и **вставьте T** с C.
   - **Как соседи подключаются к этому узлу:** «Через SSH-сервер этого компьютера».
2. **«Сохранить и запустить»**.

### 5.3. Файл экспорта A

1. **«Роль и узлы» → «Экспортировать конфигурацию»** → при необходимости **«Создать ключ»**.
2. Выберите адрес **A_AWG** (тот, по которому A виден **с B**; в списке он будет с пометкой «VPN / туннель»).
3. Флажки «публичный SSH-ключ» и «отпечаток ключа хоста sshd» — **включены**.
4. «Экспортировать» → `a-source.rcynq.json`.

## 10. Этап 6. Импорт файлов и выдача разрешений

На каждом компьютере: **«Роль и узлы» → «Импортировать конфигурацию»**. **Порядок важен: сначала B, потом второй конечный узел.**

| Компьютер | Что импортировать (по порядку) |
|-----------|--------------------------------|
| **A** | 1) `mediator-for-a.rcynq.json`, 2) `c-dest.rcynq.json` |
| **C** | 1) `mediator-for-c.rcynq.json`, 2) `a-source.rcynq.json` |
| **B** | `a-source.rcynq.json` и `c-dest.rcynq.json` (порядок не важен) |

После импорта в списке «Узлы цепочки» должно быть: на A — `MEDIATOR-1`, ниже `DEST-1`; на C — `MEDIATOR-1`, ниже `SOURCE-1`.

### 6.1. Разрешения (`authorized_keys`): что произойдёт на каждой машине

RCynQ записывает ограниченные строки `authorized_keys` сам, сразу после импорта.

| Компьютер | Что записывается | Действия от вас |
|-----------|------------------|-----------------|
| **B** | Ключ A может пробросить **только** на `C_CORP:18444`. Ключ C может пробросить **только** на `A_AWG:22` | Окно «Разрешить подключения узлов» → «Да» → UAC «Да». Строки появятся только после импорта **обоих** файлов (`a-source` и `c-dest`) — до второго импорта увидите сообщение «импортируйте также файл второго конечного узла» |
| **A** | Ключ C может пробросить **только** на `127.0.0.1:18443` (порт RCynQ на A) | То же: «Да» и UAC |
| **C** | **Ничего** | Программа скажет, что на узле без SSH-сервера разрешения не нужны. Запрос UAC не появится |

Внизу вкладки должно появиться «Подключения соседних узлов разрешены».

### 6.2. Как убедиться, что строки записаны

На B и на A (PowerShell от администратора):

```powershell
Get-Content C:\ProgramData\ssh\administrators_authorized_keys
```

Ожидаемые строки (адреса — ваши):

На **B**:
```
restrict,port-forwarding,permitopen="<C_CORP>:18444",command="exit 1",no-pty,no-agent-forwarding,no-x11-forwarding ssh-ed25519 AAAA... rcynq:source-1
restrict,port-forwarding,permitopen="<A_AWG>:22",command="exit 1",no-pty,no-agent-forwarding,no-x11-forwarding ssh-ed25519 AAAA... rcynq:dest-1
```

На **A**:
```
restrict,port-forwarding,permitopen="127.0.0.1:18443",command="exit 1",no-pty,no-agent-forwarding,no-x11-forwarding ssh-ed25519 AAAA... rcynq:dest-1
```

Это учётная запись-администратор. Если ваша учётная запись на машине **не** администратор, строки лежат в `C:\Users\<имя>\.ssh\authorized_keys`.

Если в файле `administrators_authorized_keys` на B **нет** строки с `rcynq:dest-1`: значит, импорт `a-source` выполнен, а `c-dest` — нет (или наоборот). Импортируйте недостающий файл и нажмите кнопку «Разрешить подключения узлов».

## 11. Этап 7. Проверка маршрутов вручную

Это самый надёжный способ найти проблему: вы воспроизводите ровно то, что делает RCynQ, и видите ошибку целиком. Порты `19000` и `19001` в командах — произвольные свободные локальные порты.

Ключ узла лежит в `C:\RCynQ\data\keys\ssh\rcynq_ed25519` (у каждого компьютера свой).

### 7.1. Проверка порта на C (с B)

На **B**:

```powershell
Test-NetConnection <C_CORP> -Port 18444
```

Ожидание — `True`. Если `False`: на C не запущена программа, не выбран режим «Без SSH-сервера», закрыт порт в брандмауэре (пункт 2.2) либо адрес C_CORP неверный.

### 7.2. Путь A → C

Понадобятся два окна PowerShell на **A**.

Окно 1 (команда останется «висеть» — это нормально, так и должно быть):

```powershell
ssh -i C:\RCynQ\data\keys\ssh\rcynq_ed25519 -N -L 127.0.0.1:19000:<C_CORP>:18444 <P_B>@<B_AWG>
```

Окно 2:

```powershell
curl.exe -k https://127.0.0.1:19000/health
```

Ожидание — ответ вида `{"status":"ok","role":"Dest"}`. Ключ `-k` отключает проверку сертификата, потому что он самоподписанный (RCynQ проверяет его по отпечатку сам).

Закройте окно 1 сочетанием `Ctrl+C`.

| Ответ | Причина |
|-------|---------|
| `Permission denied (publickey)` | Ключ A не добавлен на B (этап 6.1). Импортированы не оба файла на B |
| `open failed: administratively prohibited` | `permitopen` на B не совпадает с `<C_CORP>:18444`. Проверьте адрес C в файле `c-dest.rcynq.json` (поле `host`) и повторите импорт на B |
| `Connection refused` от curl | На C программа не запущена или режим не «Без SSH-сервера» |
| Зависание | Порт 18444 закрыт брандмауэром на C или маршрут B → C сломан |

### 7.3. Путь C → A (нужен для вашей цели)

Два окна PowerShell на **C**.

Окно 1 (останется «висеть»):

```powershell
ssh -i C:\RCynQ\data\keys\ssh\rcynq_ed25519 -J <P_B>@<B_CORP> -N -L 127.0.0.1:19001:127.0.0.1:18443 <P_A>@<A_AWG>
```

Окно 2:

```powershell
curl.exe http://127.0.0.1:19001/health
```

Ожидание — `{"status":"ok","role":"Source"}`. Это значит, что вся цепочка C → B → A → локальный порт RCynQ на A работает.

| Ответ | Причина |
|-------|---------|
| Зависание на первом шаге (подключение к B) | C не видит B:22 — вернитесь к этапу 0 |
| `Permission denied` на первом шаге (B) | Ключ C не добавлен на B |
| `open failed: administratively prohibited` при переходе на A | На B нет строки `permitopen="<A_AWG>:22"` для ключа C. Импортируйте на B оба файла |
| `Permission denied` на втором шаге (A) | На A не добавлен ключ C (`rcynq:dest-1`, см. 6.2) |
| Curl: `Connection refused` | На A не запущен сервис RCynQ (программа закрыта) либо порт сервиса не 18443 |

## 12. Этап 8. Диагностика RCynQ: что должно быть красным

**«Диагностика» → «Запустить проверку»** — на A и на C (на B тоже можно). По коду проверок, в этой схеме **часть красных пунктов — ожидаемая**, не пугайтесь:

| Компьютер | Проверка | Результат | Почему |
|-----------|----------|-----------|--------|
| **C** | `SshdListening` | ✗ (ожидаемо) | Проверяет sshd на C, а его там нет и быть не должно |
| **C** | остальные | ✓ | `NeighborReachability` проверяет B:22, а не C |
| **B** | `NeighborReachability` | ✗ по звену C (ожидаемо) | При импорте на B создаются звенья к A и C; проверка стучится на порт 22 у C, а у C работает порт 18444. Настоящую проверку вы уже сделали в 7.1 |
| **A** | все | ✓ | |

Красным *не* должны быть: `SshClient` на C, `NeighborReachability` на A и C (для звена B), `ChainLinkConfig`, `GitInstalled`.

Если красный `SshClient` на C — нет `ssh.exe` (пункт 2.2).

## 13. Этап 9. Первая загрузка кода с C на A

### Почему нельзя просто «нажать отправить»

RCynQ передаёт **разницу** между «базовой копией» и текущим состоянием. Базовая копия — снимок, который считается общим для обоих узлов. Она задумана для случая, когда на A и C сначала лежит один и тот же проект (это делается копированием архива — но у вас на A проекта нет).

Чтобы передать проект целиком, можно использовать такой приём: **на обоих узлах создать «пустую» базовую копию**. Тогда для C весь проект — «добавленные файлы», и первая же отправка перенесёт его на A.

> Этот приём выведен из кода (`BaselineService` копирует содержимое рабочей папки, `ConflictDetector` не считает конфликтом файл, которого нет ни локально, ни в базе, `DefaultPatchReceiver` применяет патч без конфликтов). В документации проекта он не описан, и я его не запускал на реальных машинах. На тестовой папке с 2–3 файлами проверьте его первым.

### 9.1. Пустая базовая копия на A

На **A** (папка `C:\Projects\app` должна быть **пустой**):

1. Вкладка **«Синхронизация» → «Создать базовую копию» → «Подтвердить».**

### 9.2. Пустая базовая копия на C

Задача: создать базовую копию, пока рабочая папка C пуста, а потом вернуть путь к настоящему репозиторию.

1. На C создайте пустую папку, например `C:\RCynQ-empty`.
2. Вкладка **«Роль и узлы»**: измените поле **пути к репозиторию** на `C:\RCynQ-empty` → «Сохранить». Приложение перезапустит сервис. В журнале появится предупреждение проверки `RepoValid` («не репозиторий») — это ожидаемо, сервис при этом работает.
3. **«Синхронизация» → «Создать базовую копию» → «Подтвердить».**
4. Верните путь на настоящий репозиторий → «Сохранить» (сервис снова перезапустится).

Данные базовой копии хранятся в `C:\RCynQ\data\snapshots\base` и не зависят от того, какой путь указан в настройках, поэтому смена пути обратно её не затрагивает.

> Пока на C указана пустая папка, **ничего не отправляйте** и не принимайте изменения с A.

### 9.3. Отправка

1. На C: **«Синхронизация»**. В списке «Изменения к отправке» должен появиться **весь проект** (кроме папок `.git`, `bin`, `obj`, `.vs`, `.idea`, `node_modules` — они исключены по умолчанию).
2. Проверьте список. Если в нём лишнее (например, `dist` или `packages`) — исключите (см. ниже) **до** отправки.
3. **«Отправить изменения».**
4. На A: **«Синхронизация» → «История патчей»**: строка «входящий — применён». Файлы появились в `C:\Projects\app`.

### 9.4. Что важно знать про первую загрузку

- **Размер.** Весь проект уходит одним HTTP-запросом. Приёмник принимает до 512 МБ, а отправитель ждёт ответ не более 5 минут (`RequestTimeout`). Если проект большой или канал медленный, отправка не завершится по таймауту. Исключите тяжёлые папки заранее: в `C:\RCynQ\config\syncbridge.json` на C задайте `"ExcludedDirectories"` (массив **заменяет** список по умолчанию — перечислите все нужные, включая `bin`, `obj`, `.vs`, `.idea`, `node_modules`).
- **Папка `.git` не передаётся**: она исключена всегда. На A вы получите файлы, но не историю Git. Если история нужна, RCynQ её не переносит: `git fetch` с C требует SSH на C.
- **Пустая папка на A обязательна.** Если на A уже лежат файлы с теми же именами, но другим содержимым, они станут конфликтами — patch не применится, вы увидите «конфликт» с кнопкой «Разрешить».
- **Правка `syncbridge.json`.** Закройте программу на C, отредактируйте файл, запустите снова.

### 9.5. Дальше

После первого «применён» базовые копии на A и C совпадают и содержат весь проект. Работа продолжается как обычно: правите файлы → «Синхронизация» → «Отправить изменения» (в любую сторону).

## 14. Если что-то не работает

Сначала найдите, на каком участке обрыв, пользуясь ручными проверками из этапа 7. Логи RCynQ: вкладка «Логи» и файлы `C:\RCynQ\data\logs\`.

| Симптом | Причина и решение |
|---------|-------------------|
| При отправке с C: «Patch … could not be delivered to …» и в логе `Permission denied` | Не хватает разрешений: проверьте 6.2 на B (строка `rcynq:dest-1`) и на A (строка `rcynq:dest-1`) |
| При отправке с C: `administratively prohibited` | Адрес A в файле `a-source.rcynq.json` не совпадает с A_AWG. Пере-экспортируйте `a-source` с правильным адресом, импортируйте на **B и C**, нажмите «Разрешить подключения узлов» на B |
| При отправке с A: «The certificate presented by the peer does not match the fingerprint» | На C пересоздан сертификат (удалялась папка `data`). Пере-экспортируйте файл C и импортируйте на A, затем на B |
| При отправке с A: «Node … accepts connections on its own port, so mediator … needs an SSH server» | На B не работает SSH-сервер (или B сам работает в режиме без SSH). B обязан иметь sshd |
| Патч отклонён: `InvalidToken` | Link-токены на A и C разные. Вставьте T с C на A (см. BeginnerSetupGuide, раздел 11, строка `InvalidToken`) |
| Патч отклонён: `UnknownSender` | Приёмник не импортировал файл отправителя (этап 6) |
| «Базовая копия не создана» | Этап 9.1 / 9.2 выполнены не на обоих узлах |
| Каждое изменение уходит в «конфликт» | Базовые копии разошлись. Если это первая загрузка — на A нет пустой рабочей папки или в базу на C попал настоящий проект (этап 9.2, пункт 3 сделан не при пустом пути) |
| С C в списке «Изменения к отправке» пусто после возврата пути | Приложение не сохранило путь. Проверьте «Роль и узлы» → путь к репозиторию |
| Таймаут при отправке большого проекта | 9.4: исключите тяжёлые папки |
| AmneziaWG-адрес A/B поменялся | Пере-экспортируйте файлы с новыми адресами, импортируйте у соседей и нажмите «Разрешить подключения узлов» |

## 15. Ограничения этой схемы

- **Вкладка «Ветки» и `git fetch` с C не работают** — ветки Git забираются только через SSH, а на C его нет. Отправка и приём изменений работают полностью.
- **Передаются файлы рабочего дерева, а не история Git**: `.git` исключён.
- **RCynQ не запускает и не поднимает AmneziaWG и корпоративный VPN** в этой схеме: они должны быть подключены к моменту отправки.
- **Отправка вручную.** Автоматической отправки при изменении файлов нет.
- Программа должна быть **запущена на обоих концах** в момент отправки: на A принимающий сервис работает только пока открыто приложение.
- Проверки `NeighborReachability` на B и `SshdListening` на C в этой схеме дают ложные срабатывания (раздел 12); исправлять проверки я не стал — это отдельная доработка кода.
